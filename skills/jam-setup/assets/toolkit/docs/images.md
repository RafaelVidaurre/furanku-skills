# Image routes and references

Shared by visual style exploration, asset concepts and turnarounds. Select from the actual environment; a harness or model name alone does not prove image-generation capability. Use existing skills/tools, never a replacement client.

## Discover and offer usable routes

Before the first generation offer, check **current-agent tools, Codex delegation, and configured image providers**. Read the applicable image skill and inspect the host's supported delegation mechanism; provider configuration alone is not a complete inventory. Present the relevant alternatives with their cost basis and status using the concise [image-source template](interaction.md#choose-the-image-source), then let the user choose. The inventory below is an agent reference, not a table to copy into the conversation. Recommend a suitable plan-included route when available. Reuse an explicit selection across rounds; revisit it when capability, cost or user preference changes. A capability listing is not authenticated access.

| Route | Evidence needed before offering it as ready |
| --- | --- |
| Codex built-in image generation/editing | In a Codex session, inspect the current callable tools and read its image-generation skill. A working built-in route needs no OpenAI API key or Meshy/Scenario setup. Offer it explicitly when present; an installed skill alone does not establish a callable tool. |
| Codex through delegation (direct CLI or an orchestrator) | Check the installed [Codex CLI route](codex-cli.md) and any supported orchestration surface. Offer this route even when its image tool still needs verification, with that status stated. Before generation, obtain worker evidence of the callable built-in image tool, applicable skill and image handoff. A Claude-only subagent cannot stand in for a Codex session. |
| Other native or delegated image tools | Discover callable generation/editing capability, the usage basis and a way to pass references and return images. Keep these alternatives when relevant; Codex is not the only possible native route. |
| Configured image provider | Discover the chosen provider's image-generation/editing model, input support, authenticated scope and cost path. Scenario and Meshy use [provider execution](providers.md). Other discovered services can be offered with their actual setup/integration gaps stated. |
| Find existing references online | Available image/web search or browser tools that can retrieve and display real images and source pages. Search once the user chooses this path or has already asked for research; inspect the images, not just result titles. |
| User-supplied images | The host can receive/view attachments or accessible local images. This remains an option even when every generation/search route is unavailable. |

For delegation, check the direct [Codex CLI route](codex-cli.md) as well as an available orchestrator; use the simplest supported surface that satisfies the host's routing, permissions and artifact handoff. If using an orchestrator, load its installed skill and guide. If worker capability is unknown, use a capability-only check (no image generation, image API calls, installation or auth changes), or offer “Codex — image capability to verify” until the user chooses it. The check itself uses an agent turn. Ask the worker to report its actual tool inventory and authentication mode (ChatGPT plan, API key or unknown) from supported status evidence, without account identifiers or credentials; the model name and parent tool inventory are insufficient. Report a specific missing mechanism/tool when unavailable; absence from `jam.config.json`, an orchestrator or the current session is not evidence that Codex is unavailable.

Present generation, search and supplied images as complementary paths. Discovery is complete when the user can see the applicable Codex route and configured image alternatives with their status and cost, or a concrete reason a route cannot be used. Include other discovered image-capable providers as relevant; a 3D-only endpoint is not an image-generation alternative. If no generation route works, offer image search or supplied references.

## Execute and return images

A route choice determines how images are made; the invoking skill determines whether the brief is ready. For game-style exploration, develop the [guided brief](style-exploration.md#establish-the-brief) and obtain the [round go-ahead](style-exploration.md#confirm-the-round-before-generation) before submitting or delegating generation. Use [task intent](task-intent.md) to recognize existing authorization across requests and prerequisite answers, without requiring another confirmation. Pass the resulting bounded scope and its attributable request/answer references in a style-generation worker's brief; require the worker to report missing authorization instead of generating. Preserve a selected provider while asking any missing creative question.

Follow the selected tool/skill for generation or edits, including actual reference attachments, supported output sizes and storage. An image filename in a prompt is not an attached input. For delegation, pass the brief, reference files/roles, locked choices, assigned output and cost boundary. Style exploration follows [style-image execution](style-images.md): one independent candidate per fresh session with only its own direction, plus the agreed shared constraints/references. For those gameplay-style rounds, carry the believable-gameplay requirement and carefully translated visual constraints into the worker brief and final image prompt. Keep credentials, account identifiers and private account/configuration content out of delegation briefs and artifact provenance. Name a unique shared output directory such as `Art/.scratch/style/<round>/<candidate>/`; verify shared access or use a supported file transfer when agents run on different hosts. The worker must inspect the input images through its image-viewing tool when required by its generator, copy outputs from private harness storage into the handoff directory, and return viewable images plus truthful generation provenance. Follow the environment's routing and notification ownership rules. A text answer saying “generated” is not an image handoff.

Inspect results and show them through the host's image surface before asking for a visual decision. For style exploration, follow [direct image display](#show-style-images-directly). Labels/captions belong beside the image unless the user requests text in the art. For online references, retain source-page URLs, creator/title when available, and the reason for each selection. Browsing images for inspiration does not establish permission to ship or redistribute them. Keep downloaded rights-unknown references in ignored scratch; version their source links and reference-only notes, not the image files. Use rights-cleared images for durable project image dependencies. If downloading is restricted, show the permitted preview and source link, explain the limitation, and ask for an accessible alternative only if needed.

## Show style images directly

Display each original generated image file directly in the conversation using the host's native image/attachment surface, followed by its short label/caption. Keep the originals available to open at full resolution. The user wants the images themselves: do not invoke a visualization skill or build an HTML gallery, option cards, a contact sheet or a webpage to present a style round. Do not resize, recompress, crop, dim rejected options or decorate the image before display. A viewer's automatic screen fitting is fine; preserve the actual file bytes. Create a separate presentation only if the user explicitly requests one.

If the host cannot display an original image, report that concrete limitation and provide its accessible original-file link or supported attachment. Do not silently replace direct images with HTML or text-only options. A report that generation succeeded, an HTML artifact link or an agent privately inspecting the image does not establish that the user received a viewable original.

## Cost and custody

Meshy/Scenario submissions, including delegated ones, use the existing quote, per-provider budget and intent ledger. Style exploration uses `init --exploration` without a production profile; creating a provider run requires draft project config and the selected spending authorization, not settled art direction. Keep one ledger owner across delegation and reconcile unknown submissions before another attempt.

For built-in Codex image generation within an eligible ChatGPT plan's included allowance, explain **no extra charge within the included allowance**, that image turns use the shared Codex limits several times faster, and that use beyond those limits can draw from purchased credits. State this once with the initial offer, then reuse the established cost boundary across rounds. This is a valid image-generation route for style, concepts and turnarounds, directly or through a Codex worker. It needs neither an OpenAI API key nor a Meshy/Scenario spending limit. Confirm the session's usage basis from host/account evidence or the user's established setup without displaying credentials. Other authentication/billing modes need their own cost explanation; the Codex name alone does not prove plan inclusion. Unknown remaining quota does not turn a known included route into a separately billed one; disclose the usage uncertainty and follow host routing rules.

[OpenAI image-generation guidance](https://learn.chatgpt.com/docs/image-generation) and [pricing](https://learn.chatgpt.com/docs/pricing#how-does-image-generation-count-toward-usage-limits), checked 2026-11-11, distinguish included Codex usage from API-key billing. OpenAI reports image turns use included limits about 3–5× faster on average than similar non-image turns, depending on quality and size. Pricing also says exhausted included limits can draw from purchased credits and image generation is unavailable on the Free plan. Preserve this distinction in the initial route offer; a plan-included choice does not authorize buying or consuming paid overage credits. If remaining allowance/overage behavior is unknown, state that before execution and resolve the cost boundary through the supported host controls or user decision.

Use the authorized small comparison batch and wait for direction before another round. A request to use built-in generation does not authorize switching to a separately billed API or asking for an API key. If a discovered separately billed provider has no supported budget/intent integration here, state that gap and offer a supported route; do not disguise that spend as native generation or an import. The current paid ledger supports Meshy and Scenario.

Reference discussion, search and native preview exploration do not require `jam.config.json`, a style guide or a completed asset profile. Keep preview images viewable in the conversation; copy selected files into the project before depending on them. For results produced outside the Meshy/Scenario ledger (native/delegated native tools, user uploads or web references), preserve an origin note with the true tool/source, prompt and input roles where applicable, output identity, task authorization and known/unknown usage basis. To admit those existing files into a run, use `imported` provenance with that note as `sourceEvidence`; this identifies custody, not a claim that the image was user-authored or free. Never label a Meshy/Scenario submission as imported to bypass its intent ledger. Admission to a style-bound concept/turnaround run requires resolved style and a new review; geometry additionally requires a resolved profile; preview preference is not production approval.
