# Visual style exploration

The user controls how they contribute. An attachment, a sentence, an existing game reference or “show me possibilities” is enough to start the conversation. Guide them to a useful visual brief before generating. Use the [message templates](interaction.md); accept images and free-form corrections at any point.

## Start from evidence

Read existing game notes and conversation before asking. Inspect all supplied references: one may define camera, another shapes or surface treatment, another atmosphere. A supplied role such as “use this camera” is already an answer; an unlabeled image's viewpoint is an observation, not necessarily a preference. Keep established choices distinct from observations and proposals.

For an ongoing exploration, read its `Art/.scratch/style/<round>/round.md` and the canonical style guide before asking questions. Begin the round record during brief development, before any image call. Keep a compact working brief: established choices with their user/reference sources, delegated or proposed choices, selected route/cost boundary, current request and bounded scope, candidate feedback, and the single pending decision or next action. Update it after substantive answers and reviews; carry still-valid choices into the next round. It records the conversation, not permission invented by the agent. On resume, reconcile any in-flight generation before retrying and continue from the pending decision. If records conflict with the latest user correction, apply the correction and update the record; ask only when a consequential conflict remains unresolved.

## Resolve the current image assignment

Read the latest request before inheriting the previous round's format. Determine whether the user wants competing style alternatives, complementary situations in one style, or character/outfit studies. Record the image count and what belongs in each image: subjects, outfit/genre, pose/view and reference role. A request for four characters is not automatically four alternative group scenes; when grouping is consequential and unclear, ask whether they want one image per character or the cast together. A later request for one character per image facing the camera controls that study's framing; it does not need a third-person camera behind the character. Reuse an explicit requested option count instead of reverting to the skill's default range.

Carry forward applicable user choices, not the whole prior scene. Keep user requirements, reference observations and agent proposals distinct. The agent should exercise art-direction judgment: propose coherent shape, material and palette alternatives and fill routine composition details needed to make them visible. These are exploratory choices, not new game requirements. Ask when a choice would change the game's premise, meaningful content, retained taste constraints, cost or requested deliverables. A comedic tone does not require an invented gag; avoid unsolicited narrative beats that become the focus of the comparison. A correction to proportions should not silently change every other aspect toward realism, and a missed camera target is not permission to relax it.

## Establish the brief

For a game-style round, establish these from existing context, references or a short conversation:

- **Game:** the basic premise and what the player does. A sentence is enough; no full game design document is needed.
- **Presentation:** 2D, 3D, or a defined hybrid (explain what “2.5D” means here). Ask if it is missing; top-down, anime and a 3D-capable engine do not establish dimensionality. Reuse an explicit answer such as “3D tank game” without asking again.
- **Camera rig:** the determined gameplay camera, required before any gameplay image. The camera decides whether a picture reads as gameplay or as a film still, so a label such as “third-person” or “top-down” only starts this decision. Record it in physical terms: projection, camera position relative to the player (distance and height), pitch, field of view, where the player sits on screen, its target screen height with an acceptable range, and the player's default view (for a third-person walker, usually walking away from the camera; a secondary view may face the camera). When the user gives only a label, propose a concrete rig taken from real games of that genre and ask them to confirm or adjust it. Use a gameplay reference when available. Reuse the confirmed rig verbatim in every gameplay prompt until the user changes it.
- **Subject:** a representative play situation, consistent with that game: the player/units, relevant surroundings and a visible activity. Derive it from established gameplay when straightforward; ask if choosing it would invent the game's setting, mechanics or identity.
- **Visual intent:** the qualities the user means by their style references or labels, and the constraints the images must respect. A label such as “anime,” “stylized” or “realistic” can be enough to propose a bounded visual comparison; ask what it means only when the answer would materially improve that comparison.

Ask the most consequential missing question, acknowledge the answer briefly, then continue. Start with the game when nothing is known; camera usually comes next. Develop visual intent through useful follow-ups: reference images/games and what appeals about them, proportions and shape language, surface/shading treatment, tone or setting, dislikes, and gameplay readability. Choose the next question from the actual gaps; this is not a mandatory questionnaire or a question-count target. Reuse answers, and defer details that do not affect this round, especially production budgets. A text-only question tool cannot receive images; invite attachments through the host's supported conversation surface.

Before the first broad comparison, reuse any known tastes, references and exclusions. If none are known and the user invited discovery questions, offer one easy opening: “Any visual references or strong dislikes—such as childlike proportions or busy textures—or should I explore freely?” An answer that delegates exploration is enough; do not turn this into a required aesthetic questionnaire or repeat it when the user already asked to proceed. In a resumed session, reading retained preferences comes before asking again.

Make follow-ups easy to answer: tie each to the upcoming images, offer concrete alternatives and recommend one when the brief supports it. If the user is unsure, offer to explore that uncertainty visually while keeping known choices fixed. Do not keep narrowing details that the requested comparison can answer. If the user asks to see options now, use their delegated discretion and proceed once the game, presentation, confirmed camera rig and route/cost decisions are resolved. Preserve an explicit hold or an unresolved decision the user retained.

For example, a top-down tank game with “anime-like” direction can compare distinct silhouette/shading treatments while keeping team readability and map organization fixed. Offer useful visual alternatives rather than making the user supply technical art terminology. If their references already define those qualities, move to the actual remaining uncertainty.

**Ready to act or propose:** there is enough context to explain what the next pictures will help decide, what stays fixed, and what varies. State routine exploratory assumptions briefly. Use the user's requested pace: an invitation to ask questions supports deeper discovery; “show options now” calls for a useful bounded comparison once essential scope and cost are known. An explicit hold remains a hold.

## Confirm the round before generation

First apply [task intent](task-intent.md) across the conversation. A direct request, an understood workflow invocation followed by necessary answers, or an accepted proposal can authorize the bounded round. When authorization and prerequisites are complete, give a short action summary and execute; do not ask for a second confirmation or require the exact words “Start generating.” A response such as “make B softer” can authorize that edit in context; “I like B” alone does not necessarily request new images.

When the agent is proposing a round that is not already authorized, use the [summary and question-tool procedure](interaction.md#confirm-a-style-round): show the topic-grouped brief, variations, open assumptions, route and count, then offer **Start generating** / **Ask me questions** and wait. The latter calls for an active narrowing question. Informational answers do not start an unrequested round; they may complete prerequisites for a previously requested one. Respect an explicit hold or ask-before-start instruction. Record actual request/answer references and resulting scope for every generated round; no fabricated approval. Generation authorization is separate from artifact review checkpoints. Reference discussion and brief development require no production config.

## Show a small, meaningful comparison

For open exploration, produce or find **2–4 distinct visual directions** that answer a real art-direction question for this game. Before generation, define each candidate in visible terms and explain its difference in a short caption: what changes, why it fits the brief, and the relevant tradeoff at gameplay scale. Recommend a starting direction when the brief supports one. Names such as “anime,” “stylized” or “cinematic” alone do not define useful alternatives. Near-identical palette swaps or arbitrary changes of setting do not make a meaningful comparison.

Match the breadth to the decision: before a style is chosen, offer visibly different overall treatments of both actors and environment, within the user's constraints. Once a treatment is chosen, narrow the comparison to its unresolved details. An open art-direction request should not collapse into tiny turret or trim changes. For an anime brief, possible overall treatments might use flat cel-shaded color masses, soft painted surfaces with simple shading, or angular shapes with strong inked edges; propose only treatments compatible with what this user means by anime. Explain what each would look like in play instead of relying on genre names.

Choose the view that makes the decision visible. Compare character silhouettes with readable full-body figures; test surface treatment close enough to see it; compare environment shapes in a representative space; use a gameplay view to test actor/environment cohesion and readability at player scale. Keep the subject, framing and layout comparable across competing styles unless one of those is the question. A neutral supporting study needs no invented action or gameplay HUD. Explain its role briefly and plan the relevant transfer back into gameplay; a polished character alone does not establish the whole game's look.

Exploratory variables are deliberately open: the agent may propose art treatments within the user's constraints without getting every brushstroke or prop placement pre-approved. Keep meaningful game content and explicit preferences fixed. Use proposed treatments in an already authorized comparison, labeling them as proposals; their appearance in a generated image does not make them approved canon.

When the user says the options are unhelpful, use their feedback to change the comparison, not just the labels or prompt adjectives. Identify whether the problem is off-brief content, indistinguishable treatments, weak gameplay readability or a wrong exploration axis. Reuse already stated reasons; ask one targeted question only if the cause remains unclear. Preserve still-valid choices and exclusions in `round.md`. A requested new round inherits that intent; a complaint alone is not permission for unlimited replacements.

For generated options, follow [style-image execution](style-images.md) for independent sessions, edit continuity, gameplay prompt construction and the pre-review image check. Keep map logic separate from visible decoration; “grid-based” alone must not become a drawn grid overlay.

Use [direct original-image display](images.md#show-style-images-directly), with stable labels such as A–D and one short caption per option. Name the observed difference and what to judge at gameplay scale; a caption must describe the returned image, not merely repeat the intended prompt. Use the actual reference files as generation inputs where supported, with their roles made explicit. Mark generated pictures as concepts, not engine captures.

After each round, offer refinement of any option, a specific combination of qualities, fresh directions, more user references, or acceptance. The user can answer in their own words. A refinement round keeps chosen qualities and explores narrower variations; a fresh round proposes different directions while retaining constraints the user still wants. Choosing “refine B” does not approve B as final. Do not run more batches or quietly switch providers after a failure without the applicable authorization.

Choosing a direction leads into [representative style coverage](style-coverage.md), not immediate completion. Guide a coherent set of at least three approved hero shots across the visual situations that matter for this game; propose more where needed. Coverage rounds keep the chosen style consistent while showing complementary situations, rather than repeating competing art treatments of one scene.

## Carry the decision forward

Preserve a short `round.md` beside the images in `Art/.scratch/style/<round>/`: image labels/paths, source or generation origin, per-candidate session identity when exposed, prompts/reference roles, provisional assumptions and the user's feedback. Give generation workers only the candidate-specific excerpt described in [style-image execution](style-images.md), not this all-options history. Candidates remain exploratory until the human chooses which images should define the style; “refine B” is not that decision.

As the user approves shots, preserve the **hero-shot library** using the [style custody layout](contracts.md#files-and-custody). Save partial sets as in progress; only [complete coverage](style-coverage.md) closes the exploration:

1. Copy each approved, rights-cleared image out of scratch or provider/harness storage into a new `Art/Style/<revision>/hero-shots/` directory, using descriptive names. A hero shot here is an approved visual target for the game, normally a generated gameplay mockup; it is not automatically a rendered engine capture or marketing asset. Keep the selected original bytes; any later edit gets a new file/revision. Rejected candidates and rights-unknown web images remain in scratch; retain source links/reference-only notes for the latter.
2. Save `Art/Style/<revision>/provenance.md` with a per-shot origin, image hash, final prompt/settings and input roles where applicable, relevant model/session/job identifiers, generation authorization where applicable, actual style-approval reference, and rights/source notes. For paid outputs, preserve the selected request/result, charge/reconciliation and approval evidence needed to interpret the ledger references after scratch cleanup. Copy required rights-cleared source references into that revision's `sources/` directory. Preserve the necessary selected-candidate evidence, not private logs or the whole rejected round. Required evidence must remain usable after scratch is removed; provider URLs and scratch-only paths cannot be the sole evidence.
3. Use the existing configured style document, or `Art/style.md` if none exists, as the single canonical guide. Add an embedded **Hero shots** gallery using relative image paths, with captions naming what each shot establishes (for example camera/scale, shapes, materials or lighting), exceptions and unresolved choices. Link the provenance note and record which revision is current; preserve previous revisions as history rather than overwriting them. Do not create a second competing style guide.
4. If `jam.config.json` exists, update only `style.document` and `style.references` with the guide and approved durable image/reference paths, retaining still-approved references and deliberately retiring superseded ones. Adding approved shots to the current revision leaves existing asset runs valid. When the user approves a new art direction (a new `Art/Style/<revision>/`), also set `style.revision` to that revision: this deliberately marks earlier production work stale for re-admission. If config is absent, save the guide/library now and report registration pending for `jam-setup`; provider setup and production budgets must not block saving approved art.
5. Open the saved images and verify hashes and gallery links. Check they are not ignored and that binary files use the repo's Git LFS rules; include the selected library, guide and applicable config change in the task-scoped commit under the current commit authorization. Report the hero-shot paths and distinguish saved, uncommitted, committed and pushed status. Local saving does not publish or push. Once coverage is complete, [close the exploration and clean eligible scratch](style-cleanup.md); preserve useful feedback and report any deferred cleanup.

Confirm readiness in visual terms; resolve production budget profiles later when needed for a real asset. Follow [contracts](contracts.md) for style revisions and explicit admission of exploratory concepts into production. The conversation can start without configuration; separately billed generation must first satisfy its route's spending rules.
