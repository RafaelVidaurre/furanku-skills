# Close a style exploration

Cleanup is part of completing `jam-style`, after the human approves [complete hero-shot coverage](style-coverage.md) and the library is preserved and verified. Choosing one direction or saving a partial set does not close the exploration. Perform eligible cleanup without another permission question. On resume, also finish deferred cleanup for previously closed explorations when their blockers have cleared. Age, a style hash becoming stale, and a pause in conversation do not close an exploration. Keep candidates during comparison and refinement; respect an explicit request to retain them.

## Preserve, then prune

1. Confirm the [hero-shot preservation](style-exploration.md#carry-the-decision-forward) checks passed, including readable images, matching hashes, durable evidence and gallery links. Keep a concise decision summary in that revision's `provenance.md`: what was selected, useful feedback about rejected directions, source links and the human's coverage approval. Index the associated scratch round/run paths there for future resume. In each retained scratch `round.md`, record exploration status (`open` or `closed`), its closure/approval reference and durable library path, and cleanup status (`pending`, `deferred`, `kept` or `cleaned`) with exact remaining paths, blockers or the user's keep instruction. Update this marker after cleanup; retain it so resume reads recorded scope and status rather than inferring closure from the conversation. Use project-relative paths and stable IDs; omit private account/home paths. If config is absent, saving the complete library still permits cleanup, with registration reported pending.
2. Inventory only the closed exploration's owned directories under `Art/.scratch/style/` and any explicitly associated exploration-run directories. Use filesystem and JSON inspection to enumerate exact paths, file counts and bytes; do not infer scope from a wildcard or timestamp. Check all `Art/**/run.json`, current style references/guide and known active briefs for dependencies before choosing files. Unknown ownership, unreadable records, live writers or ambiguous dependencies hold the affected directory rather than guessing.
3. Keep every `run.json` and its request, charge, reconciliation and review evidence at their existing paths, including terminal jobs. This preserves spending history and auditable references. A run with an `intent`, `unknown` or `submitted` job holds its whole directory and associated inputs/outputs until the normal provider reconciliation resolves it; cleanup never changes job state or removes locks. Keep any file still referenced by a run record or active brief, even if that record is stale. Also retain user originals, approved library revisions and anything the user asked to keep.
4. Delete only the remaining owned scratch files: rejected candidates, verified redundant copies of promoted images, temporary downloads, logs and intermediate files. Preserve useful feedback first; downloaded rights-unknown references may be removed after their source links and notes are saved. Recheck the exact deletion list against the retained paths immediately before removal, use ordinary filesystem tools on explicit paths and remove only empty directories afterward. Stay inside the inventoried scratch directories, without following symlinks into other locations. Do not sweep all scratch, private harness storage or other agents' work.
5. Verify the retained library, gallery and protected run/dependency files still exist and match their pre-cleanup hashes. Update the retained round marker with the actual removed paths/count/bytes and remaining paths/reasons. Report that deletion summary and any retained scratch with its next action, for example “provider job unresolved; reconcile before cleanup.” A blocked subset stays deferred while independent eligible files are cleaned; do not claim the whole exploration is cleaned when files were deferred. On resume, honor `kept` instructions, retry only recorded eligible deferred scope and hold legacy/missing closure evidence rather than guessing.

Approved older revisions remain versioned history. Removing that history or rewriting Git/LFS storage is a separate, explicitly requested operation. A stale production run needs re-admission, not automatic deletion. No scheduled or background garbage collector is installed by this procedure.
