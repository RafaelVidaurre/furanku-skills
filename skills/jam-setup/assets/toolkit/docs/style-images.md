# Style-image execution

Applies to generated art-direction comparisons, supporting studies and complementary hero-shot coverage in `jam-style`. The [round go-ahead](style-exploration.md#confirm-the-round-before-generation) comes first. Coverage images share the approved art direction and deliberately supplied style references while testing different approved situations; they are not competing styles. Asset turnarounds and isolated asset concepts retain their own framing requirements.

## Independent images, independent sessions

For each new independent style image, start a **fresh agent/generation session** with no previous candidate conversation or outputs. One fresh prompt or image call inside the same Codex session is not isolation. Keep the coordinator's comparison history for review, but give each generator only:

- The same relevant game/presentation constraints, this round’s framing, and deliberately selected shared reference images with their roles. Gameplay camera constraints apply to gameplay views; study framing follows the current assignment.
- That candidate's proposed visual direction and exact coordinator-written image prompt; no sibling directions, outputs, critiques or entire coordinator transcript.
- Its single-image assignment, output location, cost boundary and attributable approval reference.

Create `Art/.scratch/style/<round>/<candidate>/` with a self-contained `brief.md` for each candidate. Copy the relevant approved context and actual go-ahead reference into it; leave the all-options `round.md` with the coordinator. Each worker generates only its assigned image and writes only its own candidate outputs. Required project/host instructions still apply; other candidates' files are not input references. Record available session IDs with candidate provenance and verify they differ for independent outputs. For CLI JSON output, the coordinator can compare `thread.started` event `thread_id` values; a different output filename alone proves nothing. If the host exposes no session identity, record the fresh-launch evidence and its limits instead of claiming an ID check.

For Codex CLI, use a new top-level `codex exec` invocation per candidate, never `resume` or `fork` for independent alternatives. For an orchestrator or another agent host, create a new session without inherited conversation per candidate; sending more work to the same finished worker does not satisfy this rule. Sequential execution is fine; parallelism is optional. Even when the coordinator is Codex with a native image tool, independent alternatives need fresh image-capable sessions. For a provider, use independent requests with no prior-candidate history/reference inputs. If the available route cannot provide fresh context, report the limitation before the start decision and offer a supported route; do not silently batch in one session.

**Edit exception:** when the user wants to modify a selected image, prefer the tool's edit operation with that specific image attached. Continuing its own session is allowed when useful. Independent reinterpretations are new sessions, even when they share an approved source image. Preserve the authorized references deliberately; do not add rejected candidates as inspiration. Name the change and the invariants explicitly. The approved hair edits read: “Change ONLY the player character's hair and facial hair … Keep EVERYTHING else identical to source.png: level, props, NPCs, camera, framing, composition, lighting, rendering style, and the player's position, pose, body and outfit. Same aspect ratio and pixel dimensions.”

**Reference roles:** state in the prompt what each input image supplies and what to ignore. A character study or a style shot has its own camera, pose, backdrop and render polish, and the model copies them unless they are excluded. The approved set used “Input image 1 is IDENTITY ONLY: preserve face shape, hair, build and proportions; ignore the clothes, smile, pose, setting, framing and glossy movie rendering.” A style reference likewise names what it supplies (anatomy, face caricature, hair, materials) and what to ignore (identity, outfit, pose, backdrop, sheet layout).

Session separation reduces conversational carryover; it does not guarantee visual variety. Inspect results against the approved differences. A missing or ambiguous result must be reconciled before any retry under the existing provider/cost rules.

## Preserve the image prompt through delegation

The coordinator writes a self-contained final image prompt in the candidate's `brief.md`, separate from authorization, source notes, output paths and execution instructions. Give it the actual current image assignment; a character/outfit study keeps its requested pose/framing instead of inheriting a gameplay-camera template. For gameplay, build it from the specification below. Put framing and scale before long subject/material descriptions. Keep creative additions traceable to the user's requirements or accepted/delegated choices; strip stale scene details when the task changes.

The Codex worker preserves that prompt's creative intent and constraints. Clearer wording is allowed; a new art-direction decision is not. It may add required imagegen formatting/use-case metadata without changing subjects, count, outfits, pose, camera, scale, reference roles or treatment. It must not independently invent a joke, restage the scene, broaden the art direction or relax a failed constraint. If the prompt conflicts with the current assignment, report the conflict before generation. A broad taxonomy label such as `stylized-concept` is metadata, not a substitute for the asset type and concrete gameplay/study composition.

Return the exact prompt sent to the image tool, actual reference inputs, original image path and observed deviations. The coordinator compares it with the assigned prompt using invocation records where available; distinguish that evidence from a worker's self-report. If a prompt complied but the image failed, record image-model nonadherence; do not rewrite the user's brief to match the output. The parent remains responsible for the pre-review check below.

## Translate the brief into visible instructions

Read the selected generator's prompting guidance. The coordinator writes a concise, self-contained image prompt: do not forward the design conversation or rely on an image model to infer design intent from ambiguous prose. These requirements apply to gameplay views; explicit supporting studies use their requested frame and remain labeled as studies. The coordinator and delegated worker must both preserve them:

The goal of every gameplay image is a picture the user would believe is a **screenshot of their game in play**. The words “gameplay screenshot” alone do not produce one; the camera rig, a populated level and real-time rendering cues below do. Write the prompt in this order: frame and camera, player and activity, level, rendering, treatment, exclusions.

1. Specify **one full-screen gameplay screenshot**: a real-time screenshot of a PC/console game during play, in the agreed 2D/3D/hybrid presentation and aspect ratio. Retain the requested stylized treatment; “gameplay” does not imply photorealism or prove engine origin. Keep option labels, explanatory text and HUD/UI out of style images; HUD is a separate decision, and adding it never fixes a wrong camera or composition.
2. Copy the confirmed **camera rig** from the [brief](style-exploration.md#establish-the-brief) in physical terms, never as distance words. For a third-person game this reads like: camera about 3.5–4 m behind and 2 m above the player, slight downward pitch, about 75° field of view, player horizontally centered, full body visible with feet in the lower third, about 25% of image height and never over 30%, most of the frame showing the level. For an overhead game it gives the projection, height/pitch and unit size (for example, each tank about 5% of image width). Hold the rig, aspect ratio and actor scale fixed across art-direction alternatives; only a camera comparison varies them. Image models enlarge the player: across two style sessions, every image overshot the requested size. Distance words (“usual gameplay distance”, “slightly above”, “small”) produced players at 76–88% of image height; a physical rig with a field of view, “never over” and “most of the frame shows the level” produced 41–58%. Ask for the low end of the agreed range, and judge results against the range.
3. Show the **player doing the game's common verb** from the brief, for a third-person walker usually walking away from the camera mid-stride, with a neutral face that does not look at the camera, and the destination or interaction target readable at this scale. Use only established or delegated game content: no invented gags or story beats.
4. Build a **populated level in play** around the player: modular architecture, abundant props and set dressing, and, where the game has them, several NPCs in the same style going about their own business, with traversable space and the world continuing past every frame edge. For a bounded arena or puzzle board, show its actual playable boundaries instead. A sparse stage with a few posed characters reads as a diorama or character showcase. In the approved style-definition set, props and busy NPCs were what made the frame read as a level. Use display plinths, cutaway slabs or lineups only when they belong to the agreed presentation or an explicitly requested study.
5. Describe **how a real-time engine draws the frame**: game-ready models with limited polygons, simplified silhouettes, solid sculpted hair and cloth modeled into the mesh, simple skin shading; modular environment pieces, tiling textures, lower detail in the distance; one directional key light, crisp shadow maps, flat-ish ambient, screen-space ambient occlusion, neutral exposure, everything in focus. Treatment words borrowed from film or painting (“feature-animation”, “painterly”, “atmospheric”, “studio lighting”, “cinematic”) pull images toward film stills and illustrations; express a treatment as model, material and lighting properties instead.
6. Translate mechanics into visible outcomes only when relevant. A placement grid describes spatial organization, not necessarily markings. For an unmarked grid-based map, describe regularly aligned paths/obstacles on continuous ground, with a short explicit exclusion of drawn grid lines/coordinate overlays. Visible tiles, seams or tactical grid overlays are separate visual choices; include them only if requested or approved.
7. Add the candidate's agreed **visible art treatment**: silhouette/proportions, surfaces, shading, palette organization and detail density as relevant. Keep the shared scene specification identical; change only the intended art variables. Art treatments come from the user, an approved reference role or the proposed exploration; routine composition choices may support them without becoming new game requirements. Replace vague style names with observable features. Avoid dramatic lighting or spectacle that hides the shapes the user must compare. Translate production terms into the result they produce in a shipped game before prompting. “Low-poly” from a game team usually means limited-polygon, game-ready models with simplified silhouettes and smooth shading. Prompting “visible flat polygon facets, each facet one even color” produced literal faceted art that the user rejected as far too geometric. Use a literal reading only when the user asks for that look, and ask when the two readings would produce different images.
8. Prefer positive descriptions of the intended composition, with a few precise exclusions for known failure modes. Check terms that may be drawn literally (grid, tile, miniature, board, cinematic, hero shot). In generator prompts, translate “hero shot” into the specific gameplay view it represents. A style-only reference supplies its approved treatment; its poster composition or close-up camera does not override the gameplay-frame specification.

Example **only when these choices were approved**, including the framing, arena content and candidate treatment:

> One 16:9 full-screen gameplay screenshot mockup of a 3D multiplayer tank battle during play. Fixed high overhead orthographic camera showing the playable arena; each tank is about 5% of the image width. Red and blue tanks move between low walls, leaving open lanes wide enough for vehicles to pass. Ground and surrounding structures fill the viewport. Paths and cover align in regular modular spacing on continuous, unmarked ground; no drawn grid overlay. Rounded hulls and oversized turrets remain readable at this scale, with crisp cel-shaded color blocks, restrained surface detail and clear red/blue team separation. Even gameplay lighting keeps tanks, obstacles and traversable ground distinct. Single view, without a presentation border or display pedestal.

An approved third-person prompt from the style-definition session, which the user accepted as credible gameplay, abridged:

> Generate exactly one landscape 16:9 image: a credible real-time third-person 3D gameplay screenshot in a populated medieval market level, no HUD. Input image 1 is IDENTITY ONLY: preserve the young man's face shape, hair, lanky adult build and stylized adult proportions; ignore the clothes, smile, pose, setting, framing and glossy movie rendering. The player wears a simple linen tunic, walking away up the street mid-stride with his back to the camera, relaxed neutral face if visible, never looking at the camera. Horizontally center his full body at approximately 25% of frame height, never over 30%, feet in the lower third; prioritize this small gameplay scale. Camera approximately 3.5–4 metres behind him, 2 metres above ground, slight downward pitch, 75-degree field of view, showing extensive level ahead and around him. Timber-framed houses, produce stalls, carts, barrels, crates, a well, and several NPC merchants and townsfolk shopping and walking. Game-ready models with limited polygons, simplified silhouettes, solid sculpted hair, modeled cloth and simple skin shading. Modular environment geometry and tiling textures. Daylight directional lighting, crisp shadow maps, flat-ish ambient and screen-space ambient occlusion, neutral game exposure, everything in focus. No text, UI, chibi, photorealism, posing, animated-film gloss, illustration, cinematic lighting, depth of field, lens effects, bloom haze or film grading.

The result still placed the player at about 41% of image height, inside the range the user accepted.

The worker brief must contain the completed scene specification and its candidate treatment, not instructions for the worker to invent those choices. The examples' subjects, projections, ratios and measurements are not defaults for other games; the rig numbers come from this game's confirmed camera. An explicitly requested close-up/asset study can supplement gameplay views, with its role labeled; it does not establish gameplay-scale readability.

## Inspect before offering a style choice

Open every returned image and check it against the current assignment. For gameplay views, measure the player's height as a fraction of image height (feet to top of head) and its horizontal position, and record both against the rig's range in `round.md`. Then ask whether a player would believe this is a screenshot of the game: camera height and pitch, populated level, real-time rather than film rendering. Also check understandable play space/activity, requested presentation and treatment, reference roles, and absence of unrequested markings or display framing. For character/outfit studies, check subjects per image, pose/gaze, requested outfit/genre and consistent treatment; do not fail a requested front-facing study for lacking a behind-player camera. Compare alternatives at normal viewing size: are their intended differences visible, and are the relevant subjects and details readable?

Record what each candidate can establish and its concrete mismatches in `round.md`. A beautiful diorama, poster or close-up that misses a requested gameplay frame cannot establish gameplay readability. Show that limitation plainly; do not treat choosing its aesthetic as accepting its wrong camera. A flawed result may still reveal useful shape or material preferences: separate those findings from the failed requirement and carry them into the next relevant test. Offer the useful subset honestly; fewer than two distinct options that answer the round’s question leaves a competing-options comparison incomplete. A requested single-image edit or coverage shot needs only its assigned result. Report any gap and the specific correction needed; any regeneration follows the existing authorization, reconciliation and cost rules. Do not silently retry or switch providers. A generated mockup remains a concept, never evidence that the game or assets run in-engine.


## When composition instructions repeatedly fail

If a round repeatedly misses the same camera or scale constraint, identify that failure before proposing more images. In the next authorized attempt, change the composition strategy: simplify competing detail demands, describe the amount of visible foreground and surrounding play space, or use an available reference explicitly for camera/layout only. Preserve reference permissions and any fresh-image/no-reference instruction. Do not keep spending on the same prompt with stronger adjectives or present any strategy as guaranteed. If the needed reference is unavailable or the generator still misses, report the unresolved limit and retain useful treatment findings separately.

Prioritize deviations by the visual decision: wrong actor scale can invalidate a gameplay-readability test; missing expressions matter for an acting game. Incidental dressing is not automatically a failure unless it changes the premise, violates a constraint or distracts from the comparison. Likewise, cel shading is a valid 3D game treatment; a single image that reads flat does not establish that the technique is unsuitable for 3D.
