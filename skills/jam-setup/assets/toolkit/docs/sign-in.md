# Sign-in handoff

Use this procedure when provider setup needs browser approval or client trust. The agent prepares and verifies the connection; the human signs in. Complete one provider's handoff before asking about another.

1. Inspect the supported tool's status. Reuse verified access. Treat an installed command, registered MCP server, authenticated account and working capability as separate observations. Inspect each failed command and explain its effect before claiming a batch succeeded.
2. Start the provider's supported login and read its actual instructions promptly, including stderr. Retain its process handle or resumable flow locally. A running command does not mean a browser opened or the user received instructions.
3. Deliver a visible instruction packet **before** asking about completion: provider name, where to act (browser, terminal or named client), exact steps/link, expected success indication, and what the agent will verify next. Never replace this with “Have you signed in?” or make the human inspect collapsed tool output.
4. If the host withholds progress until the turn ends, use the provider's supported resumable flow and end the turn with the local instructions. Resume the same flow on the answer. If progress is visible and a running process can be awaited, show the instructions immediately and await that process. Use the active host's supported mechanism; do not invent a login helper, token store or background waiter.
5. Use the active question/notification mechanism when human action is needed. Its safe instructions must stand alone, even if earlier commentary is hidden. Ask readiness with choices such as “Approved” and “Could not complete,” never ask for credentials. If the login completes observably, verify it directly and close any pending readiness request; a redundant “Done” reply is unnecessary. If the human reports no visible prompt, re-show the current instruction packet as a normal visible local message, not collapsed tool output. For hidden progress, use step 4; for unavailable private delivery, use the fallback below. Reuse the current login while valid; only confirmed expiry/failure warrants a fresh flow.
6. Verify through the supported status and free access checks. Report each provider as verified, pending a specific human action, or failed with the actual reason. A human's “Done” is a signal to verify, not proof of authenticated access. Continue the original task within its authorization.

## Private login material

Display only the provider's intended user-facing sign-in instruction on a local surface allowed by the host. For Meshy this can include `user_code`; `device_code`, tokens and stored credentials are never displayed. Keep resumable flow IDs local. The `--no-wait` verification URL may embed the user code and must stay local too. Never place codes, code-bearing links, tokens, private config or logs in notifications, synced questions, screenshots or repository files. Where notifications are enabled, send only safe directions to the local instructions or browser prompt.

If the host cannot deliver the user-facing login instruction privately, explain the limitation and give the official human-run desktop command instead (for Meshy, `meshy auth login`). State which machine and terminal to use and that it opens a browser for approval; leave that terminal running until success. This is the fallback for unavailable private delivery, not the default handoff. Never ask the human to paste anything back.

## What the human should receive

Populate these examples with observed state; placeholders are not a usable handoff.

- **Meshy, local instruction:** “Open [the CLI's verification URL], sign in to Meshy, enter [the CLI's user code] if prompted, and approve Meshy CLI. The page should confirm approval. I’ll then verify the CLI connection and balance without generating anything.” Show the real user-facing link/code only on the permitted local surface. A notification can instead say: “On your development computer, follow the Meshy approval instructions in the local agent chat, then approve in your browser. Has the page confirmed approval?” It must not contain the code or a code-bearing link.
- **Scenario in Claude Code:** “In your interactive Claude Code session, run `/mcp`, select `scenario`, and choose its authentication action. Sign in to Scenario in the browser and approve access. Return when the client reports the connection is authenticated; I’ll verify it by listing teams.” If that interface is unavailable in the current host, identify how to open an interactive Claude Code session on the same machine/user rather than telling the user to enter `/mcp` somewhere that cannot handle it. If the server is absent, fix registration first.
- **Scenario in Codex:** “I’ve started Scenario sign-in. Approve access in the browser prompt opened by Codex. I’ll verify the connection afterward.” Use this only when the command actually started; if a URL or client action is needed, deliver that actual instruction through the permitted local surface first.
