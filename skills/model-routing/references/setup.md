# Agent-guided routing setup

Read when setting up routing for a machine or project, reviewing the current setup, or editing existing preferences. Setup works with the native routing agent and existing configuration; it needs no gateway account or selector service.

1. Run `router.py setup --repo <root>` and read the returned policy, sources, questions, preferences, and configuration layers. Present the current effective setup using `setup_overview` and the [message guidance](message-templates.md), even when `setup_complete` is true. A completed setup is still editable. Inspection uses saved configuration, without live quota probes or model calls. Finish when the user can see the current behavior, defaults, and relevant overrides in ordinary language.
2. Offer to keep the current setup, change settings, or inspect scope/role overrides. If the user already named a change, proceed with that change instead of asking what to edit. Keeping the setup ends the flow without writes; unanswered onboarding choices remain unanswered. During first-time setup, ask only the returned missing choices the user wants to configure. During editing, ask only what is needed for the requested changes, including already-configured fields. Display the response duration alongside the stop/continue choice. Finish when the user keeps the setup or the requested changes are concrete.
3. Resolve the persistence scope: `global` (all projects), `repo` (shared project settings), or `machine-repo` (this project on this machine). Reuse an explicitly requested scope; otherwise show the current source and ask where the change should apply. Put only the changed recovery fields in a JSON object and generate a preview:

   ```sh
   python3 <skill-dir>/scripts/routing_setup.py preview --repo <root> \
     --scope <scope> --file <choices.json>
   ```

   `--role commander|captain|worker` targets that role; `--route <id>` targets recovery on an existing exact route in the chosen layer. Define a missing route through `config.py` first, so setup never copies a launch tuple into a new scope implicitly. For model preferences, candidate states, exact launch tuples, or account policy, use the existing [configuration interface](configuration.md) and [account policy](accounts.md); recovery preview accepts recovery fields only. Finish when the intended write and its effective result are known, including any more-specific override that would hide the change.
4. Present the human-readable `setup_change_preview`: changed settings, current → proposed values, destination scope, and effective result. Keep the full machine preview for applying; show raw JSON only when requested. Obtain any missing approval, then apply that exact artifact through `routing_setup.py apply --file <preview.json>` (or the existing configuration writer for other settings). A changed input requires a fresh preview and review. Finish when the save reports success and a readback confirms the effective result; summarize what changed and where it applies. Keeping existing values produces an unchanged result, not another onboarding cycle.

The router's `setup --setup-file <choices.json> --scope <scope>` and `setup --apply-setup <preview.json>` expose the same preview/apply flow. Inspection and preview perform no writes and read no live credentials. Apply locks all three persisted layers in canonical path order, revalidates the preview, then atomically replaces the target while retaining those locks through effective-policy inspection. Ordinary config writes and deletion share these locks. A competing writer is refused; locks owned by another process are preserved. Reapplying a completed preview leaves the config untouched. Other routes, preferences, candidate settings, quota account configuration, and role policies are preserved.

Optional customization stays in the existing configuration interface: inspect `config.py models` for allowed launch combinations and state, edit ordinary `preferences` for model or provider intent, and use candidate overrides for allowed models. [Accounts](accounts.md) covers quota-account selection. Recovery policy contains behavior and bounds, not model favorites or a second provider registry.
