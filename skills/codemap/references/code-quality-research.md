# Code quality criteria for codemap's generic facts

Research note, 2026-09-23. This recommends checks for the codemap pipeline; it does not claim that a metric alone diagnoses bad design. The cited sources establish the design principles or the history-based techniques. The scanner proposals below are adaptations to codemap's component and file graph; Jev must make the architectural judgments.

## Evidence codemap has today

The current [scan](../scripts/scan.py) records tracked files, lines, source/test role, units, resolved file imports with paths and lines, unresolved imports, contract files found by name, and commits touching each file in a 90-day window ending at the scanned commit. The [skeleton](../scripts/skeleton.py) aggregates production imports to modules/components, counts distinct incoming and outgoing neighbors, computes `fan_out / (fan_in + fan_out)`, and finds strongly connected groups. The [draft and Jev contract](jev-decisions.md) add evidence-backed responsibilities, intended areas, runtimes, natures, roles, and typed decisions. These are **observations**. Whether a boundary is useful, a dependency is harmful, or two jobs should be separated is an **architectural judgment**.

The criteria are language agnostic because they use paths, imports, units, history, contracts, and roles. Today's import extractor covers JavaScript/TypeScript, Rust, and Python; an unsupported language or many unresolved imports means weaker graph evidence, not a clean bill of health. An import edge is a source-code dependency, not proof of a runtime call or a deployment dependency.

## Candidate criteria

### 1. Mixed responsibility and weak cohesion

- **Plain meaning:** A component owns two independent reasons to change, especially when different users or workflows drive them. Parnas's original modularization criterion is to hide design decisions likely to change; Martin frames a module's responsibility by who asks it to change. [Parnas, *On the criteria to be used in decomposing systems into modules*](https://doi.org/10.1145/361598.361623); [Martin, *The Single Responsibility Principle*](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html).
- **Generic detection evidence:** For persistent classification doubt after the evidence pass, or an explicit mixed-responsibility note during triage, collect the two proposed jobs, the file/module paths implementing each, and the independent consumers, contracts, or documented workflows. A component with two distinct module clusters, contract families, or audience claims is a review candidate. An uncertain area/runtime/nature/role answer alone is only an uncertainty signal.
- **Ownership:** Scanner reports paths, module grouping, contracts, imports, and previous Jev uncertainty. Agent supplies cited repository evidence; Jev decides whether the two named jobs really represent separate reasons to change and whether the finding is warranted. A suggested split names which paths would move, without pretending to prove a refactor is safe.
- **False-positive limit:** Thin composition roots, facades, adapters, and intentional shared kernels may mention several concerns while owning one coherent job. A shaky classification can instead mean missing facts or weak criteria. Do not turn every `unsure` badge into a quality finding; require two demonstrable jobs and paths after the evidence pass.

### 2. Cyclic production dependencies

- **Plain meaning:** Two or more independent components require each other, making their change and release boundaries less independent. Martin's Acyclic Dependencies Principle addresses package cycles and describes extracting a shared package or inverting a dependency to break one. [Martin, *Design Principles and Design Patterns*, pp. 17–21](https://objectmentor.com/resources/articles/Principles_and_Patterns.pdf).
- **Generic detection evidence:** Strongly connected groups of at least two components in the directed **production** import graph, plus a concrete path and import line for each edge of a representative cycle. Module-level cycles can be shown as supporting detail; the existing root/barrel-module exception should remain.
- **Ownership:** Scanner owns the graph fact and the evidence paths. The agent can write a plausible separation from repository evidence; Jev need not decide whether the cycle exists. If a future policy lets Jev accept a cycle by design, preserve the observed cycle separately from that verdict.
- **False-positive limit:** Test-only imports, re-export/root-module patterns, and loops inside one deliberate component do not establish a bad component boundary. Missing dynamic dependencies can hide cycles; unresolved imports should lower confidence in graph completeness.

### 3. Dependencies crossing an intended boundary

- **Plain meaning:** The system's rules should not import a concrete delivery or I/O detail that is meant to be replaceable; source-code dependencies should follow the declared architecture. Martin's Dependency Rule makes this distinction between inner policy and outer mechanisms. [Martin, *The Clean Architecture*](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html).
- **Generic detection evidence:** Production imports from a Jev-classified `core` component to an `adapter`; client-to-server or server-to-client imports that bypass a genuinely shared contract; product imports of test/tooling/experiment units. Attach importer/imported paths and line, both cards, role/runtime/nature decisions, edge reason, and any relevant contract file. These correspond to codemap's existing checks.
- **Ownership:** Scanner supplies and filters edges; Jev judges architectural acceptability where roles or deployment boundaries matter. The scanner can flag product-to-support imports as a direct structural fact when both natures are resolved. The agent can describe a contract move or dependency reversal from repository evidence; Jev only makes the typed acceptability decision.
- **False-positive limit:** An import can be type-only, a re-export, an entry-point composition step, or a deliberately shared build artifact. A filename that looks like a contract does not prove it is the actual interface. Runtime flows absent from imports also mean the graph cannot validate all layering rules.

### 4. Dependency direction, positional stability, and stable abstractions

- **Plain meaning:** A component many others depend on is expensive to change and should avoid depending on easily changed details. Martin calls this positional stability, distinct from how frequently code changed; his Stable Abstractions Principle adds that heavily depended-on packages should be extensible through abstractions. [Martin, *Stability and Dependency*, pp. 7–11](https://objectmentor.com/resources/articles/stability.pdf).
- **Generic detection evidence:** For each production component edge `A -> B`, report distinct-neighbor `fan_in`, `fan_out`, and `I = fan_out / (fan_in + fan_out)` on each endpoint. `I(A) < I(B)` is a deterministic **candidate** for a stable component importing a less stable one. Show the gap and the import examples. A high-inbound component with no clear contract/port evidence is a separate stable-abstraction review candidate.
- **Ownership:** Scanner owns degree, ratio, and candidate edges. Jev decides whether the direction conflicts with the components' intended change boundaries. It can judge stable abstraction qualitatively only when the cards or repository documents identify an actual interface/port and how dependents extend it; contract filenames and role labels merely prompt that review. With no such evidence, record the abstraction question as unassessable instead of a finding.
- **False-positive limit:** Martin counts external **classes** for his package metric; codemap currently counts distinct adjacent **components**, so its ratio is an analogous graph measure, not his exact metric. A small graph makes ratios jump with one edge. High historical churn is not the same as structural instability. A concrete but intentionally frozen data package may be fine; a `kernel` label or schema file alone cannot establish extensibility.

### 5. Hubs and broad coupling

- **Plain meaning:** A component with many dependents has wide potential impact; one importing many peers has a broad change surface. The counts locate review targets, while Martin's account of incoming dependencies and Stable Abstractions explains why a heavily depended-on unit needs a coherent, stable interface. [Martin, *Design Principles and Design Patterns*, pp. 22–26](https://objectmentor.com/resources/articles/Principles_and_Patterns.pdf).
- **Generic detection evidence:** Rank production components by distinct incoming/outgoing neighbors, show their consumers/dependencies and representative file imports, and connect the rank to role, contracts, size, and mixed-responsibility evidence. The graph fact is `used by N` or `uses N`; it is not itself a defect.
- **Ownership:** Scanner owns counts and rankings. Jev decides whether the hub is a deliberate contract/kernel or an unrelated collection of jobs and concrete dependencies; only the latter should become a quality finding, with the offending paths named.
- **False-positive limit:** Entrypoints and orchestrators naturally have high outgoing degree; shared contracts naturally have high incoming degree. One import to a package root can aggregate many uses. Raw import count overweights repeated statements, so use distinct neighbors for candidate ranking and paths for explanation.

### 6. Change coupling across boundaries

- **Plain meaning:** Files or components that repeatedly change together may share a hidden responsibility or change requirement even without an import. Gall, Hajek, and Jazayeri introduced release-history analysis to uncover logical coupling; CodeScene's own method explicitly treats co-change as context-dependent. [Gall et al., *Detection of logical coupling based on product release history*](https://ieeexplore.ieee.org/document/738508/); [CodeScene, *Change Coupling*](https://codescene.io/docs/guides/technical/change-coupling.html).
- **Generic detection evidence:** This needs per-commit sets of touched paths, grouped into components, with pair co-change count, each component's change count, time window, and example commit IDs. Compare repeated cross-component pairs to import and contract boundaries. **Current scan's per-file `changes` totals cannot recover which files changed together**, so this criterion requires more deterministic scan data before implementation.
- **Ownership:** Scanner would calculate pair counts and supporting commits. Jev would decide whether the co-change is unexpected for the declared boundaries; the agent would write any plausible split or shared contract from repository evidence. Neither side should infer a defect from one joint commit.
- **False-positive limit:** Source and test updates, generated files, release/version sweeps, formatting, migrations, and large commits produce expected co-change. Independent commits for one task can hide coupling; short or sparse history can make pair rates unstable. A pair's co-change never proves a source dependency.

### 7. Size and activity hotspots

- **Plain meaning:** Large code that is revisited often deserves attention first; this is a review-priority signal, not evidence that its design is bad. CodeScene explicitly uses lines as a **proxy** for complexity and change frequency as a proxy for effort. [CodeScene, *Hotspots*](https://docs.enterprise.codescene.io/versions/2.0.0/guides/technical/hotspots.html). Nagappan and Ball's original study found relative churn measures more useful than absolute churn in one industrial system. [Nagappan and Ball, *Use of Relative Code Churn Measures to Predict System Defect Density*](https://www.microsoft.com/en-us/research/publication/use-of-relative-code-churn-measures-to-predict-system-defect-density/).
- **Generic detection evidence:** Current file-level `loc` and 90-day `changes` support a two-axis ranking of production files, then rollup to their component without treating summed commit counts as unique component commits. Attach the window, file path, lines, and touches. Show it alongside a structural finding to help prioritize that finding.
- **Ownership:** Scanner owns ranks and the activity window. Jev should judge actual quality only when another criterion provides architectural evidence; the hotspot alone stays an observation in Size & activity or a priority badge.
- **False-positive limit:** Lines are not semantic complexity; generated files, vendored files, new features, incident response, commit style, and the chosen window skew rankings. A large stable file or a small frequently changed file need not be poor quality. Do not display a defect prediction or a universal numeric threshold from these proxies.

## Implementable shortlist for this codemap change

| Order | Result | Exact boundary between fact and judgment |
| --- | --- | --- |
| 1 | Keep production component cycles and existing boundary-crossing checks as findings. | Scanner supplies actual import paths; Jev judges role/runtime-dependent exceptions; the agent writes any suggested repair from evidence. |
| 2 | Add `does more than one job`. | A candidate comes from persistent doubt or an explicit mixed note, with an evidence pass and two named jobs and paths; Jev confirms genuine mixed responsibility. Missing evidence or a weak rubric stays an uncertainty/skill issue. |
| 3 | Add `widely used part imports a less stable part`. | Scanner proposes every production component edge where both ratios exist and `I(source) < I(target)`, with the ratio gap and import paths; Jev accepts or rejects the architecture concern. Keep structural stability separate from git activity. |
| 4 | Add `hub needs review` only when Jev finds an incoherent or concrete high-impact boundary. | Scanner ranks distinct-neighbor fan-in/fan-out and shows the top candidates; high degree by itself stays a metric. Jev can combine the hub with mixed-responsibility evidence; assess Stable Abstractions only when a documented interface/port exists. |
| 5 | Use current size/activity data to prioritize confirmed findings. | Keep hotspots out of the defect count unless another check supplies a defect. |
| Later | Add change coupling after the scanner records per-commit changed-path sets. | Pairwise co-change cannot be reconstructed from today's file totals; Jev judges whether a repeated pair is unexpected. |

The numeric candidate rules above are *codemap policy proposals*, not measured universal cutoffs. The original empirical work on component metrics found no one metric set that predicts defects best across systems, which supports showing evidence and letting the architecture decide rather than calling every high count a defect. [Nagappan, Ball, and Zeller, *Mining Metrics to Predict Component Failures*](https://www.microsoft.com/en-us/research/publication/mining-metrics-to-predict-component-failures/).
