# Routes to a clip

A route is one way to get the motion: keyed **by hand** on the project rig, **retargeted** from a clip that already exists, or generated by a **motion provider**. Which ones exist depends on this machine, the project's accounts and what the person allows, as they stand in this session.

## Choosing

1. **List what can be called.**
   - By hand: someone will key (the person, or you from the key poses) in a program that runs here and exports the clip format (clip-spec.md); Blender runs here when `blender --version` (or `jam doctor`) shows it.
   - Retarget: there is a source clip the project may use (its own capture, a library it licenses, another character's clip) and its skeleton has a skeleton map. Ask where it comes from and what its licence allows.
   - Provider, with the toolkit: `jam provider list` shows each provider's capabilities; one serves this route when it lists `motion` in a mode the clip needs (the modes and when each fits are in the toolkit's `docs/providers.md`, "Motion"). Then `jam provider probe <id>` for each candidate and settle every `unknown` as that page says. A provider is callable only when that succeeded in this session.
   - Provider, without the toolkit: ask the person which motion-generating tools, services or agent skills they have and may use here, and read each one's own documentation for its modes, limits and terms.

   When a provider's transport is a skill, load that skill: it states its host requirements (some need particular hardware or another machine) and how files reach that host; the route is callable only when those are met or the person arranges them.
2. **Price each callable route** in the provider's own unit, the way its descriptor's `quote` (or its own pricing) says, and in words for the person (time for a hand-keyed clip).
3. **Offer** every callable route that fits the purpose, with its cost, what it needs from the person, and which skeleton its motion arrives on (a provider's is its descriptor's `rig.landmarks`; `capabilities.motion.note` says when it animates only its own auto-rigged copy of the mesh). The person chooses. When nothing callable fits what they allow, do as the toolkit's `docs/providers.md` "Routes" says.

Done when the route, the provider and model or source clip, the expected cost and the person's choice are written down.

## By hand

Key the clip on the project rig, in any program that exports the clip format.

1. Start from the key poses. `jam python <S>/blockout.py <clip.json> <clip-blockout.glb> [--length <s>] [--loop-end open|duplicate]` writes a clip already in the clip format: the project rig with one animation on every frame, each bone carried from one key pose to the next (rotations slerped, translations linear, travel straight between poses). It is a blockout, not the motion: timing, arcs, overlap, held feet and everything that makes the action read are keyed afterwards, by the person or with their animation tool. The frame count follows clip-spec.md ("A loop's last frame").
2. Open the blockout (or the rig with the key-pose file) in the animation program, at the spec's `fps` over the clip's frames, and key the motion between the poses. Hold planted feet still in the world (an IK target per foot keeps them still while the body moves); put travel on the hips, or on the spec's root bone, as the body would travel. Step 5 of the skill moves or removes it to match the spec.
3. Export a `.glb` in the clip format: +Y up, the rig and its mesh, this one animation, sampled on every frame. In Blender's Python: `bpy.ops.export_scene.gltf(filepath=..., export_format="GLB", export_yup=True, export_animations=True, export_animation_mode="ACTIONS", export_force_sampling=True)` with only this action in the file. Blender's glTF importer and exporter both convert times by the scene's frame rate, so set it to the spec's `fps` (`scene.render.fps`, with `fps_base` 1 for a whole rate) before importing the blockout.

Done when the clip's `.glb` exists and `clip_check.py --measure-only` (with `--travel-velocity 0,0` for an in-place spec: nothing has been taken off the clip yet) reports `animations`, `skeleton`, `wholeFrames` and `length` passed in `checks`.

## Retarget an existing clip

Hand the work to the `jam-3d-retarget` skill with files: the source clip, the source skeleton's map, the project rig (`rig.model`) and its map (`rig.map`), the spec's frame rate, and how it should find contacts: its foot-contact speed is in source heights per second, so convert the spec's `contacts.detect.speed` with the divisors that skill prints. It returns the clip on the project rig. A source the person supplies goes on record with where it came from and the evidence that the project may use it.

Done when the clip on the project rig exists and the retarget's report says it passed.

## A motion provider

1. Read the provider's page or skill (the descriptor's `docs`) and the live schema of the operation: inputs, limits, plan access.
2. Build the request from the spec:
   - `inbetween`: the key poses, and whatever else the provider's page or skill asks for (such as a few frames of context leading into the motion, keyed on the project rig like the key poses), on the provider's skeleton. When that is not the project rig, `jam-3d-retarget` moves each file onto it, with the project map as the source map and the provider's skeleton map (its skill's map file, or the descriptor's `rig.landmarks` written to a file) as the target map.
   - `text`: a prompt from `purpose` and the action, and the length.
   - `video`: the footage.
   - `library`: the action's id from the provider's catalog.

   When the provider's own tooling asks for a tolerance, take it from the spec's `accept`: a floor or ground tolerance (how far a foot may sit from the ground) is `accept.penetration`, a seam or jump tolerance (how far a joint may jump where generated pieces meet) is `accept.boundaryJump`. A tolerance the spec has no field for is the person's, asked as clip-spec.md says.
3. A paid provider runs as one job through the run ledger, exactly as the toolkit's `docs/providers.md` "One paid job, start to finish" says (`jam job open`, `jam job submitted`, `jam job done`). An unbilled one (local, or included in a plan) is recorded with `--tool`.
4. Download every output into the run folder at once and leave the originals untouched; later steps work on copies.
5. Output on another skeleton goes through `jam-3d-retarget` onto the project rig, with the descriptor's landmark map for the source. Keep any contact flags the provider returns as evidence; check.md says how the check treats them.

Done when any job is settled and the clip on the project rig exists.

## What the motion step records

In a run, the `motion` step records the clip as the route returned it, with where it came from:

| Route | Command |
| --- | --- |
| By hand | `jam run record <id> motion --file clip=<clip> --tool "<program and version>, keyed by <who>" --note "<from the blockout or not>"` |
| Retarget | `jam run record <id> motion --file clip=<source clip> --source "<where the clip came from>" --source-evidence <licence or origin document> --tool "<source>" --note "..."`, then the `retarget` step as `jam-3d-retarget` says |
| Provider, paid | `jam run record <id> motion --file clip=<output> --job <job> --tool "<provider, model and version>" --note "..."` |
| Provider, unbilled | `jam run record <id> motion --file clip=<output> --tool "<provider, model and version>" --evidence <request> --evidence <result> --note "..."` |
