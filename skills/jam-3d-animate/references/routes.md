# Routes to a clip

A route is one way to get the motion: keyed **by hand** in Blender, **retargeted** from a clip that already exists, or generated by a **motion provider**. Which ones exist depends on this machine, the project's accounts and what the person allows; find out each time instead of assuming.

## Choosing

1. **List what can be called.**
   - By hand: Blender runs here (`jam doctor` shows it), and someone will key: the person, or you from the key poses.
   - Retarget: there is a source clip the project may use (its own capture, a library it licenses, another character's clip) and its skeleton has a skeleton map. Ask where it comes from and what its licence allows.
   - Provider: `jam provider list` shows each provider's capabilities; one serves this route when it lists `motion` with the mode the clip needs:

     | Mode | Fits when |
     | --- | --- |
     | `inbetween` | the spec has key poses and the motion between them is wanted |
     | `text` | the motion is described in words |
     | `video` | the person supplies footage of the motion, and has the right to use it |
     | `library` | a stock action fits the purpose |

     Then `jam provider probe <id>` for each candidate and settle every `unknown` as the toolkit's `docs/providers.md` says. A provider is callable only when that succeeded in this session. When its transport is a skill, load that skill: it states its host requirements (some need particular hardware or another machine) and how files reach that host; the route is callable only when those are met or the person arranges them.
2. **Price each callable route** in the provider's own unit, the way its descriptor's `quote` says, and in words for the person (time for a hand-keyed clip).
3. **Offer** every callable route that fits the purpose, with its cost, what it needs from the person, and which skeleton its motion arrives on (a provider's is its descriptor's `rig.landmarks`; `capabilities.motion.note` says when it animates only its own auto-rigged copy of the mesh). The person chooses. When nothing callable fits what they allow, say which routes exist and what each would need; do not hand over a lesser clip without saying so.

Done when the route, the provider and model or source clip, the expected cost and the person's choice are written down.

## By hand

Key the clip in Blender on the project rig.

1. Open the rig (the `.blend`, or import `rig.model`). Set the scene frame rate to the spec's `fps` and the frame range to the clip's frames: `length × fps` frames for a loop that ends one frame before its first pose comes round, one more when it repeats the first pose, `length × fps + 1` for a clip that does not loop.
2. Start from the key-pose file (`keyPoses.file`) when there is one: import it and keep its action; every key pose sits on its frame.
3. Key the motion between the poses. Hold planted feet still in the world (an IK target per foot keeps them still while the body moves); put travel on the hips, or on the spec's root bone, as the body would travel. Step 5 of the skill moves or removes it to match the spec.
4. Export a `.glb`: +Y up, the rig and its mesh only, this action only (remove the others), sampled on every frame, named after the clip. In Python: `bpy.ops.export_scene.gltf(filepath=..., export_format="GLB", export_yup=True, export_animations=True, export_animation_mode="ACTIONS", export_force_sampling=True)`.

Done when the clip's `.glb` exists.

## Retarget an existing clip

Hand the work to the `jam-3d-retarget` skill with files: the source clip, the source skeleton's map, the project rig (`rig.model`) and its map (`rig.map`), and the spec's frame rate. It returns the clip on the project rig. A source the person supplies goes on record with where it came from and the evidence that the project may use it.

Done when the clip on the project rig exists.

## A motion provider

1. Read the provider's page or skill (the descriptor's `docs`) and the live schema of the operation: inputs, limits, plan access.
2. Build the request from the spec:
   - `inbetween`: the key poses, and whatever else the provider's page or skill asks for (such as a few frames of context leading into the motion, keyed on the project rig like the key poses), on the provider's skeleton. When that is not the project rig, `jam-3d-retarget` moves each file onto it, with the project map as the source map and the provider's skeleton map (its skill's map file, or the descriptor's `rig.landmarks` written to a file) as the target map.
   - `text`: a prompt from `purpose` and the action, and the length.
   - `video`: the footage.
   - `library`: the action's id from the provider's catalog.
3. A paid provider runs as one job through the run ledger, exactly as `docs/providers.md` "One paid job" says (`jam job open`, `jam job submitted`, `jam job done`). A local or included one is recorded with `--tool`.
4. Download every output into the run folder at once and leave the originals untouched; later steps work on copies.
5. Output on another skeleton goes through `jam-3d-retarget` onto the project rig, with the descriptor's landmark map for the source. Keep any contact flags the provider returns: the check stamps them into its report beside its own contacts (`--provider-contacts`), never instead of them.

Done when the job is settled and the clip on the project rig exists.

## What each route records

The `motion` step records the clip as the route returned it, `jam run record <id> motion --file clip=<clip> --note "..."`, with where it came from:

| Route | Add |
| --- | --- |
| By hand | `--tool "Blender <version>, keyed by <who>"` |
| Retarget | `--source "<where the clip came from>" --source-evidence <licence or origin document>`, then the retarget step as `jam-3d-retarget` says |
| Provider, paid | `--job <job>` |
| Provider, local or included | `--tool "<provider, model and version>"`, and the request and result files as `--evidence` |
