---
name: jam-3d-animate
description: Make or check an animation clip for a rigged humanoid character on the project's own rig. Defines the clip with the person (frame rate, length, loop, in-place or root motion, ground, key poses, acceptance thresholds), chooses a route the setup allows (keyed by hand, retargeted from an existing clip, or generated by a motion provider), puts travel where the spec says, and checks the clip for foot slide, ground penetration, jumps and loop seams, with a pose sheet and a video. Use when the user asks to make an animation clip for a rigged character, to check an existing animation clip, or when a recipe run reaches its animation steps.

# Animation clips

Four words carry this skill. The **clip spec** (`clip.json`) says what one clip must be, from the person: frame rate, length, loop, root convention, ground, key poses and the thresholds the check enforces. **Key poses** are named poses on the project rig at their times. A **route** is how the motion is made: by hand, by retargeting a clip that exists, or by a motion provider. The **clip check** measures any clip, however it was made, on the project rig against the spec. What a clip file is, and where every number comes from, is in [references/clip-spec.md](references/clip-spec.md).

`<S>` is this skill's `scripts/` folder. The Blender scripts need Blender 5.1 or later (`blender --version`; they stop with a message on an older one); the others need Python 3 with numpy. When Blender is missing, ask the person to install it or to name the program they animate in: any program that exports the clip format serves the by-hand route, and the check then needs Blender wherever it runs.

In a project with the jam toolkit, `jam` is `node tools/jam/jam.mjs`, paths are project-relative and every script runs from the project root (`jam blender <script> -- <arguments>`, `jam python <script> <arguments>`). Without the toolkit the same scripts run from the project root as `blender --background --python-exit-code 1 --python <script> -- <arguments>` and `python3 <script> <arguments>`; each script's header lists its arguments. When the toolkit is missing and wanted, use the `jam-setup` skill.

A clip that is to be delivered into a project with the toolkit is made in an `animation` recipe run: `jam run start animation <clip id> --brief-text "<what the clip is for, on which character>"`, then follow `jam run next <clip id>`, which names the step that is due and the command that records it. Exploring motion, or checking a clip nobody will deliver, happens outside a run, with the same steps and no records.

## Make a clip

1. **Define the clip.** Read [references/clip-spec.md](references/clip-spec.md) and settle every field with the person.

   `jam python <S>/clip_spec.py <clip.json>`

   Done when it exits 0 and the person has accepted the spec. In a run: `jam run record <id> define --file spec=<clip.json> --tool "jam-3d-animate clip_spec.py" --note "<purpose; who set the thresholds>"`.

2. **Key poses**, when the spec lists them. Pose the project rig for each one and keep each pose as an action (or animation) named exactly as in `keyPoses.poses`, in a `.blend` or `.glb` beside the rig (or as animations of `rig.model` itself). Then:

   `jam blender <S>/keyposes.py -- <clip.json> [--poses <file with the pose actions>]`

   It writes the spec's `keyPoses.file` (one key per pose at its frame), a manifest beside it with the extension `.json`, and a pose sheet beside it (`<name>-sheet.png`, one still per pose with its name). Done when it exits 0 and the person has seen the pose sheet and accepted every pose. In a run: `jam run record <id> keyposes --file keyposes=<keyPoses.file> --evidence <manifest .json> --evidence <pose sheet> --tool "Blender <version>, jam-3d-animate keyposes.py" --note "..."`; without key poses, `jam run skip <id> keyposes --reason "..."`.

3. **Choose the route.** Read [references/routes.md](references/routes.md): list the routes this setup can actually call, price each, and offer them with their cost; the person chooses. Done when the route, the provider and model or source, the expected cost and the person's choice are written down.

4. **Make the motion** by the chosen route (routes.md has each in full, with what each records):
   - **by hand**: key it on the project rig from the key poses (`<S>/blockout.py` gives a starting clip) and export the clip format;
   - **retarget**: hand the source clip, its skeleton map, `rig.model` and `rig.map` to the `jam-3d-retarget` skill;
   - **provider**: load its page or skill, run a paid job through the ledger (`jam job open` … `jam job done`; an unbilled one is recorded with `--tool`), keep the outputs untouched, and have `jam-3d-retarget` bring motion on another skeleton onto the project rig.

   Done when a `.glb` with the motion on the project rig exists and any job is settled. In a run, record the clip as the route returned it (`motion`), then `retarget` as `jam-3d-retarget` says, or `jam run skip <id> retarget --reason "the motion is on the project rig"`.

5. **Put the travel where the spec says.**

   `jam blender <S>/root_convention.py -- <clip.glb> <clip.json> <out-dir> [--travel line|hips] [--animation <name>]`

   In-place takes the overall travel off the hips and keeps their bob, sway and turns; root motion puts the travel on `root.bone` (the hips keep the rest, every joint stays where it was) or leaves it on the hips. `--travel line` reads travel as a constant velocity (cycles); `--travel hips` follows the hips exactly (starts, stops, clips whose speed changes). It writes the clip, holding this one animation, and `travel.json`. Done when it exits 0 and `travel.json`'s `hips` shows it: for in-place, `after.alongRange` is the hips' own motion with the travel gone and `heightRange` unchanged; for a root bone, `overRoot` shows what stayed on the hips.

6. **Check the clip.**

   `jam blender <S>/clip_check.py -- <clip.glb> <clip.json> <out-dir> [--travel <travel.json> | --travel-velocity <vx>,<vz>] [--provider-contacts <file>]`

   An in-place clip needs `--travel` (the file from step 5) or `--travel-velocity` (`0,0` for a motion that never travelled). Without `contacts.detect` in the spec, add `--contact-height <m> --contact-speed <m/s>` from the person. It writes `clip-report.json`, `clip-sheet.png` and, when an encoder is found, `clip.mp4`. Read [references/check.md](references/check.md) for what each number means and what to do when one fails.

   Done when it exits 0 (`"passed": true`), every entry in `unmeasured` and `unjudged` has been judged by the person from the sheet or video, and you have looked at the sheet and video and can state that the motion does what the purpose says, or which fault it shows. A failure goes back to step 4 or 5 through check.md's table; a threshold changes only as clip-spec.md says.

7. **Deliver.** In a run, record the check; the check and the delivery are a person's to accept, as the toolkit's `docs/review.md` says (a review request, or their words relayed):

   `jam run record <id> check --file clip=<clip.glb> --file evidence=<out-dir>/clip-report.json --file evidence=<out-dir>/clip-sheet.png [--file evidence=<out-dir>/clip.mp4] --tool "Blender <version>, jam-3d-animate root_convention.py and clip_check.py" --note "<root convention and travel reading, anything unmeasured or unjudged and the person's judgement>"`

   Putting the clip into an engine is the `jam-engine` skill's `import --kind animation`, when the adapter has it (`jam engine show`); otherwise the step's condition is unmet and `jam run next` passes over it. Then:

   `jam run record <id> delivery --file clip=<clip.glb> --file evidence=<out-dir>/clip-report.json --tool "<the tool recorded at check>" --note "<the same judgement of anything unmeasured or unjudged>"`

   Both notes name every key of the report's `unmeasured` and `unjudged` word for word (such as `footSlide` or `groundTravel`), each with how the person judged it: the toolkit's `clip-report` check refuses a record whose note leaves one out.

   Done when `jam run next <id>` says every step is settled and `jam run deliver <id>` passes. Outside a run, done when the person has the clip, `clip.json`, the report, the sheet and the video, with your finding.

## Check a clip made elsewhere

Any humanoid clip can be checked: write a spec for it with the person (step 1; `keyPoses` may be left out), with `rig` naming the skeleton the clip is on and its map. A clip meant for the project rig but on another skeleton goes through `jam-3d-retarget` first. Then step 6, with `--travel-velocity` for an in-place clip. To see a clip's numbers before anyone has set thresholds (a bought clip, a first try), add `--measure-only`: the spec may then have no `accept`, the report holds the measures and judges nothing. Done as in step 6, or, measuring only, when the person has the report with your reading of it.

## What is validated

[references/validation.md](references/validation.md) lists every run with its numbers. In short: on generated walk cycles with faults of known size, the check read a planted foot's slide (also one too fast for detection, once its window is declared, and put it to the person when not), a sunken foot's penetration, a pop at either end next to a jump inside the clip, a jump inside the clip and an unclosed loop to within a few millimetres, and passed the clean clip, at 30 and at 29.97 fps; the root convention removed travel while keeping the pelvis bob and sway, and moved travel onto a root bone with every joint left in place. On a bound test humanoid, a clip keyed from a blockout and a generated clip each went through the whole `animation` recipe and were delivered; generated stepping clips failed on penetration and jumps, with their dragging feet put to the person; on a captured walk, travel at ground height is ordinary swing, which is why the check leaves it to the person. Not validated: real characters, captured or library motion through the whole check, keying by a person, turning or terrain-crossing clips. `python3 -m pytest <S>` runs the unit tests and, when Blender is found (`JAM_BLENDER`, else PATH), the Blender tests.
