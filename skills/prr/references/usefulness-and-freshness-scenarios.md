# Usefulness and freshness scenarios

Read when screening a difficult candidate or maintaining the skill. Apply the main skill's What belongs and Read and use rules. These cases are manual regression checks, not measured agent reliability.

| Evidence or record | Expected judgment |
| --- | --- |
| “Users can restore a named document version; automatic history is bounded.” | Product behavior: retain the recovery promise and agreed retention boundary. |
| “Be methodical, research libraries, get an adversarial review.” | Development guidance. It does not authorize new product obligations about signing keys, quorum protocols, or internal schema fields. |
| “Use this runtime.” | An authoritative engineering choice, normally an ADR. If the product promises plugins compatible with that runtime, preserve the compatibility promise in PRR. |
| “Test locally with real email files through the production ingestion interface.” | Development workflow. Separately preserve any product requirement to import email files or process billing deterministically. Approval does not make the workflow a product requirement. |
| “The demo succeeded on a phone last month.” | Historical evidence. It is neither an ongoing requirement nor evidence that all supported platforms are accepted. |
| “For this repair, preserve these 155 entries and leave 15 unmatched forms raw; do not change routes.” | Bounded repair instructions and evidence. A separate supported principle such as not inventing canonical meanings can belong in PRR; fixture counts and frozen routes do not become permanent product policy. |
| An open question asks how to prepare for paid access; newer accepted entries define paid access. | Partly stale decision. Reconcile the answered portion from later authority; preserve independently unresolved product choices. Do not discard the entire question blindly. |
| A feature is implemented, but its requirement is tentative and no later decision exists. | Implementation evidence does not promote commitment. Verify user evidence or leave the decision unresolved. |
| “The prototype season ends at 30 turns or when one player survives.” | A valid phase-scoped gameplay rule. It does not become clutter merely because it says prototype; later phases need an explicit scope decision. |
| “Does the current loop improve retention?” | Research question. A product choice such as whether to require delayed mastery before unlocking content can be an open PRR entry. Keep the study plan in research. |
| “Use this exact button wording” or “this flow has no confirmation dialog.” | Potentially valid product decisions. Small or visual does not mean unimportant; check supported scope and future design consequence. |
| “Prefer existing libraries” for a product that orchestrates agents. | Determine the actor: instructions to its developers belong in repo guidance; a user-configurable rule governing agents operated through the product may belong in PRR. |
| A current implementation disagrees with an accepted requirement. | Implementation drift until later user authority proves a changed target; never rewrite intent merely to make the audit green. |
| An old entry uses an outdated product name but remains semantically valid. | Identity/history issue, not evidence the requirement is obsolete. Stable IDs survive title changes. |
| “Make recovery reliable,” followed by already-recorded precise resume/no-loss guarantees. | No new standalone entry unless the statement adds a distinct boundary. Attach necessary rationale to the existing owner. |

Done when: a review distinguishes valid detailed or technical product constraints from process, evidence, and unsupported design choices, and distinguishes stale decisions from implementation gaps.
