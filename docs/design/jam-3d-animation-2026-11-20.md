# 3D character animation in the jam skills

**Status:** design, 2026-11-20. Epic `furanku-skills-xfu`. Research:
[MotionBricks](../research/motionbricks-best-practices-2026-11-20.md),
[generative animation providers](../research/generative-3d-animation-providers-2026-11-20.md).

## Goal

A person can get an animation clip for a rigged humanoid character, made the way their setup allows:
keyed by hand, retargeted from an existing clip, or generated by any motion provider. One check
judges every clip the same way, on the project's own rig. Nothing assumes an operating system, GPU,
engine, rig, remote machine or game genre beyond a tool's own documented requirements, which a skill
states and checks. What happened on any one project is never a rule.

## Pieces and who owns what

| Piece | Owns | Knows nothing about |
| --- | --- | --- |
| `jam-3d-animate` (skill) | the clip spec, key poses on the project rig, choosing a route, the clip check, delivery | any one provider, any engine |
| `jam-3d-retarget` (skill) | moving animation between two humanoid skeletons through landmark maps | where the animation came from or goes |
| `jam-3d-motionbricks` (skill) | MotionBricks: host requirements, setup, request packing, generation, unpacking, NVIDIA's usage rules, the SOMA landmark map, licence rules | the project rig (it works on SOMA only) |
| toolkit: `motion` capability | provider descriptors for motion generators, `jam provider list/probe` | any one provider's API |
| toolkit: `animation` recipe | the step order and what each step records | how a step is done |
| engine adapters: `import --kind animation` | putting a clip onto a skeleton already in the engine | how the clip was made |

Skills hand work to each other as files only. A skill never reads another skill's folder; when it
needs a file another skill ships (a landmark map), it takes it as a path argument.

## Shared file contracts

### Clip file
A glTF 2.0 binary (`.glb`) holding the skinned rig and exactly one named animation when delivered. `jam-3d-animate`'s clip-spec reference is the definition. glTF frame:
metres, `+Y` up, the character faces `+Z`, `+X` is its left. Frame rate is the clip spec's, sampled
on whole frames. Engines convert in their adapter, never in these skills.

### Skeleton map
The existing landmark-map format (`label`, `notes`, `landmarks`: bone name → landmark), the same
vocabulary `jam-3d-rig` and provider descriptors (`rig.landmarks`) already use. Every skeleton a clip
lives on is described by one: the project rig, SOMA, a provider's output skeleton, a library's.
Bones at no landmark (twists, rolls, fingers a source lacks, attachment bones) are listed as
unmapped and keep their rest pose; they are never guessed.

### Clip spec (`clip.json`, written by `jam-3d-animate`)
Schema `tools/jam/schemas/animation-clip.schema.json`. Fields:
- `id`, `purpose` (one sentence: what the clip is for);
- `rig`: the project rig `.glb` and its skeleton map;
- `fps`, `length` (seconds, or a range), `loop` (boolean);
- `root`: `in-place` (travel removed, pelvis motion kept) or `root-motion` (travel on a named root
  bone, or on the hips when the rig has no ground root);
- `ground`: `flat`, or a description of the height change the clip must cross;
- `keyPoses`: named poses with their intended times, stored in `keyposes.glb` (the project rig with
  one animation holding one key per pose);
- `contacts` (optional): which feet or hands should be planted when;
- `accept`: thresholds the check enforces — foot slide while planted, penetration below ground,
  boundary jump at the first and last frames, loop seam. Every threshold comes from the project
  (its budget, the person); the skill ships no default numbers.

### Clip report (`clip-report.json`, written by the clip check)
Measured on the final clip on the project rig: per contact window, slide and penetration; boundary
and seam jumps per bone; frames, fps, length; which thresholds pass. Contacts are detected on the
target rig from foot height and speed, never taken from a provider's contact flags (those may be
reported beside it). Plus a pose sheet (`clip-sheet.png`) and, when a renderer is available, a
video.

## Routes in `jam-3d-animate`

1. **By hand** in Blender on the project rig, from the key poses.
2. **Retarget** an existing clip (library, mocap, another character) with `jam-3d-retarget`.
3. **A motion provider**: any provider whose descriptor serves `motion` in the mode the clip needs.
   Its output is on the provider's skeleton; `jam-3d-retarget` brings it onto the project rig.

The route is chosen from what `jam provider list` / `probe` and the person allow, like image and
mesh routes. Paid providers go through the run ledger (`jam job ...`).

## The `motion` capability

`capabilities.motion` in a provider descriptor, with `modes` from:
- `inbetween` — motion between given poses;
- `text` — motion from a written prompt;
- `video` — motion captured from footage;
- `library` — preset clips applied to a rig.

The descriptor's `rig.landmarks` names the provider's output skeleton. A provider that only animates
its own auto-rigged copy of a mesh says so in `capabilities.motion.note`; its clips still reach the
project rig through retargeting. A descriptor states only what its provider's own docs say, and adding
one is not an endorsement.

Which descriptors ship (from the survey): a provider gets `motion` only when an agent can reach it
through a transport the contract knows (`cli`, `mcp`, `skill`, `browser`, `agent`) and its terms allow
an agent to drive it and a game to ship the output.
- Existing descriptors gain `motion`: Meshy (`library`, `text`), Tripo (`library`), Scenario (the modes
  its MCP server actually exposes).
- MotionBricks (`inbetween`) through the `jam-3d-motionbricks` skill.
- Others the survey found usable (hosted text/video services, open models such as Kimodo) get a
  descriptor only with a working transport; the survey in `docs/research` records them, and a project
  may describe one in `jam/providers/<id>.json`. Providers whose terms bar agent use, commercial output or ML use, or whose access is
  gated, are not described.

## MotionBricks pipeline (inside `jam-3d-animate`'s provider route)

```text
keyposes.glb + context (project rig) ──jam-3d-retarget──> SOMA poses (.glb)
  ──jam-3d-motionbricks pack──> request.json ──generate (on a qualifying host)──> result.json
  ──jam-3d-motionbricks unpack──> generated.glb (SOMA) + contacts.json
  ──jam-3d-retarget──> clip on the project rig ──jam-3d-animate check──> clip-report.json
```

- `pack`/`unpack` run where Blender is; `generate` runs where MotionBricks' requirements are met.
  Those may be one machine or two. The skill names the files to move and assumes no transport.
- `generate` uses only MotionBricks' own environment and plain JSON, so the generating host needs no
  Blender and no jam toolkit.
- Requests record model revision, precision, backend and settings; results are reproducible only on
  the same backend and precision.

## The `animation` recipe

`define` (clip spec) → `keyposes` (optional) → `motion` (the route) → `retarget` (when the motion is
on another skeleton) → `check` (clip report) → `import` (optional, when the engine adapter supports
`import --kind animation`) → `delivery`. Roles: `clip` (model), `keyposes` (model), `evidence`.

## Engine import of a clip

`import --kind animation` takes a clip whose skeleton matches a skinned asset already in the engine
(the receipt of that import, or its engine id) and prints the animation asset ids. An adapter that
cannot do it says so in `jam engine show`; the recipe step is then skipped. Unreal implements it.

## Naming

Skills that only work in 3D carry `3d` in their names: `jam-3d-animate`, `jam-3d-retarget`,
`jam-3d-motionbricks`, and the renamed `jam-3d-model`, `jam-3d-retopo`, `jam-3d-uv`,
`jam-3d-texture`, `jam-3d-rig`.

## Validation

Each skill's `references/validation.md` lists what was run, on what, with numbers, and what was not
validated. A run on a particular machine is evidence of that run, not a requirement.
