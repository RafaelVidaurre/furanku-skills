# Repository-aware codemaps

Date: 2026-09-23 · Work: `furanku-skills-2cp.22` · Infrastructure: `furanku-skills-2cp.21`

## Decision

Separate **repository landscape**, **project purpose**, and **views of behavior**. A repository is a storage boundary, not necessarily a product boundary. A project may combine an API, game simulation, desktop editor, and deployment definitions. One exclusive repository-type label loses that structure.

A landscape sits above the existing system picture only when Jev confirms multiple independently meaningful projects. Package count alone does not justify it. Tightly coupled applications and their shared libraries normally remain one project. Independently used tools can be separate projects even when they share packages. Shared components remain single records with multiple project memberships; they are not copied or forced into a fictional product.

Each project has a Jev-selected primary kind for orientation. Views are independently assessed from supplied evidence, so a game can have request and infrastructure views; a library can have a compiler pipeline. Type is never a hard filter. Unsupported or ambiguous classifications keep a generic system picture.

## Why these views

This is a selection of questions, not a requirement to fill every diagram. The general separation of landscape, dynamic behavior, and deployment follows the [C4 diagram categories](https://c4model.com/diagrams). C4's [deployment diagram](https://c4model.com/diagrams/deployment) explicitly describes a particular environment; repository declarations cannot establish what is currently deployed.

| Project kind | Engineers' question | Helpful view and minimum evidence | Usually omit unless independently useful |
| --- | --- | --- | --- |
| Web service / API | What happens to this request, and where can it stop? | Request path: entry, routing, ordered middleware, handler, domain operation, I/O, response or rejection. Read registrations and their execution semantics, plus one concrete request. | Game loop; a library shipping matrix with no libraries |
| Game / simulation | What advances a frame or tick, and who owns state? | Game loop: input, fixed/variable update, simulation, replication/rendering, repeat edge and timing notes. ECS: entities, component data, systems, read/write and scheduling relations, only when source/docs establish ECS. | A pretend linear request story for the simulation |
| Library / SDK | Where do callers enter, and how do extensions and dependencies fit? | Library API: public entry points, internal seams, callbacks/adapters and external APIs. Read exports, examples and extension registration. | People-to-server traffic or an empty Ships in matrix |
| CLI / developer tool | How do arguments become work and an exit result? | Command path: parse/dispatch, config, action, I/O, output/errors. Read executable entry, command registration and one command implementation. | Deployment view without a deployment |
| Data pipeline / ETL | What depends on which dataset and when is it recomputed? | Data pipeline: sources, transforms, sinks, orchestration and retry/checkpoint boundaries. Read job definitions and data contracts. | Request/response arrows for batch work |
| Mobile / desktop / interactive app | What owns state across input, backgrounding and shutdown? | App lifecycle: startup, UI events, state/storage, background work and teardown. Read lifecycle hooks, subscriptions and navigation/state ownership. | Server layers imposed on a local app |
| Compiler / interpreter | How does input become executable output or a diagnostic? | Compiler stages: parsing, intermediate representations, passes, execution/emission, diagnostic branches. Read pass registration and IR boundaries. | Client/server grouping with no such runtimes |
| ML system | How do training artifacts reach serving, and what differs at inference? | ML lifecycle: data prep, training/evaluation, artifact publication/loading, inference. Read actual job/serving definitions and artifact references. | A single line implying training runs per request |
| Embedded / firmware | What runs at boot, on interrupts, and on the scheduler? | Device lifecycle: initialization, tasks/interrupts, shared state, hardware I/O and watchdog/failure paths. Read scheduler setup, entry points and hardware interfaces. | Network traffic unsupported by the hardware/config |
| Infrastructure / IaC | Where does declared traffic enter, run and persist? | Infrastructure: named environment, ingress/gateway, service instances, queues/stores, hosting boundaries and protocols. Read deployment/resource/config declarations and references to code. | Code-import arrows presented as traffic |
| Other / mixed | What is here and where should I start? | Existing system/area/component views; propose a named behavior view only with concrete evidence. | Empty or speculative specialist views |

The [game loop](https://gameprogrammingpatterns.com/game-loop.html) has different time semantics from a request: processing input, updating and rendering repeat and may have different rates. [ECS separates identity, component data and system behavior](https://docs.unity.cn/Packages/com.unity.entities%400.9/manual/ecs_core.html); these are labels inside an ECS view, distinct from codemap's package-level component. These established practices motivate the views, not framework-specific parsers or assumptions that every game uses ECS.

The remaining view choices are design inferences from established practices: [middleware order and short-circuiting](https://learn.microsoft.com/en-gb/aspnet/core/fundamentals/middleware/?view=aspnetcore-5.0) motivates request branches; [commands, groups and parameter context](https://click.palletsprojects.com/en/stable/commands-and-groups/) motivates command paths; [API clarity at the point of use](https://www.swift.org/documentation/api-design-guidelines/) motivates caller-centered library maps. [Airflow tasks and dependencies](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/) motivate data lineage, [Android lifecycle transitions](https://developer.android.com/guide/components/activities/activity-lifecycle) motivate app state views, and [LLVM pass organization](https://llvm.org/docs/NewPassManager.html) motivates compiler stages. [TFX training and serving workflows](https://www.tensorflow.org/tfx/guide/understanding_tfx_pipelines) motivate distinct ML phases; [Zephyr interrupts](https://docs.zephyrproject.org/latest/kernel/services/interrupts.html) and [scheduling](https://docs.zephyrproject.org/latest/kernel/services/scheduling/index.html) motivate firmware execution contexts. These are examples of engineering questions across ecosystems, not stack detection rules.

## Evidence and judgment

1. Scanner: collect facts, including a sorted tracked-path inventory that survives unsupported source languages, manifest/document/deployment filenames, existing component metadata and dependency facts. A filename is a reading lead, never proof of project kind, middleware order or network topology. Keep existing language-aware import extraction and disclose its coverage separately.
2. Agent draft: read repository docs, entry/registration code and deployment files. Propose project boundaries with component IDs, shared memberships, purpose, relationships and path evidence. Describe each view's question, concrete scope/scenario, nodes, directed labeled edges and per-node/per-edge evidence. Read source contents; evidence paths alone cannot tell Jev why a decision is justified, so summary/detail carries the grounded fact. When a graph claim needs code-level support, draft-only `evidence_excerpts: [{path, start_line, text}]` supplies bounded exact source passages, independently of the proposed graph. Only questions citing those paths receive them; text participates in fingerprints and authors recheck it when cited files change. Excerpts stay out of the viewer map. Live request acceptance exposed this transport gap: accurate graph descriptions alone did not provide the classifier independent source contents.
3. Jev: select repository shape (`single`, `landscape`, `abstain`), primary project kind, component-to-project memberships (independent boolean judgments, permitting sharing), and whether each proposed view is supported and useful. Proposed projects and view graphs are authored interpretations until judged. Only accepted memberships and view decisions are shown; uncertain/abstaining decisions remain explicit in output diagnostics. Never invent graph ordering, project ownership or missing entities from imports.
4. Builder: validate references, bounded view graphs, evidence and unique IDs; mechanically assemble accepted selections. Cache all decisions by full question/state/criteria fingerprint, bump the global instruction version, preserve provider-failure behavior. Re-evaluate repository/view decisions even when component `holds` carries old component attributes forward.

## Shared implementation contract

Optional additions preserve existing drafts/maps. New draft-template output includes empty `projects`, `project_relations` and `views`; old drafts with none use the existing system picture.

Draft `projects`: `[{id, name, summary, purpose, components: [componentId], evidence: [path]}]`. Jev gets all project cards and their proposed memberships. `project_relations`: `[{from: projectId, to: projectId, label, detail, evidence: [path]}]`; these are repository-evidenced project relationships, not inferred package coupling.

Draft `views`: `[{id, project: projectId, kind, title, question, scope, summary, evidence: [path], nodes: [{id, label, kind, detail, component?: componentId, evidence: [path]}], edges: [{from: nodeId, to: nodeId, label, detail, kind, evidence: [path]}]}]`. `scope` names a request, tick, command or declared environment. Node `kind` is practitioner vocabulary (middleware, system, component data, gateway, datastore, stage). Edge `kind` is one of `control`, `data`, `network`, `file`, `process`; loops and branches are explicit edges. Node order is reading order, not a claim of execution without edges. Component references link back to real code; nodes may represent concepts absent from the import scanner.

The shipped view kinds are `request`, `game-loop`, `ecs`, `library-api`, `command`, `data-pipeline`, `app-lifecycle`, `compiler`, `ml-lifecycle`, `device-lifecycle`, `infrastructure`. One bounded directed-graph renderer supports all; specialist layout algorithms are deferred.

Map additions: `landscape: {enabled: boolean, decision: {value, status, confidence, reason}}`, `projects` with the draft card plus accepted `components`, resolved `kind` and `decision`, `membership_decisions: [{component, decision}]`, `project_relations`, accepted `views` with a `decision`, and `view_decisions` diagnostic records for every proposed view. Builder and viewer workers must agree any necessary refinements here before diverging. `view_decisions` entries are `{id, project, kind, decision}`; a confidently false boolean decision has status `rejected`. Primary kinds are `web-service`, `game`, `library`, `cli`, `data-pipeline`, `application`, `compiler`, `ml`, `embedded`, `infrastructure`, `other`. Graphs are bounded at 32 nodes and 64 edges. Existing `schema: codemap.map/1` and existing required fields stay compatible.

The builder accepts 1–7 explicit areas per system picture (per project when the landscape is enabled, rather than a repository-wide cap; actor/external/component readability bounds follow the same scope) and an area containing product code without a runnable; this enables libraries and small projects without inventing extra products. An area still requires components. A repository with zero parsed components may have zero explicit areas and evidence-backed projects with empty membership: conceptual views still work on unsupported languages or IaC-only trees, while import coverage is explicitly limited. Empty membership is not evidence that a project does not exist. Existing system flows continue to require their established runnable/person/external endpoints. Concept-level behavior belongs in a view, never a fabricated runnable. A project-scoped view filters components/areas/flows/actors/externals to that project's accepted members, preserves shared components in each applicable project, and drops orphaned relationships.

## Viewer

`#/` opens a landscape when enabled; otherwise the existing system picture. Landscape project cards explain purpose, kind, shared components and relationships; first click shows their card, second click or an explicit button opens `#/project/<id>`. The project page uses the existing purpose layout with project-scoped data and links to the supported views. `#/view/<id>` shows a view's title, question, scope, graph and evidence cards. A route to the whole repository keeps code without accepted project membership reachable. Unknown IDs degrade safely. Back/parent paths preserve project context.

Existing lenses remain reachable. Empty irrelevant lenses are omitted from the current project selector when their data is empty; no project type dictates hidden facts. New specialty views are offered only when accepted. Color continues to mean area, neutral for infrastructure/concept nodes without a code owner; edge styling explains only relationships present on that screen. No diagram turns a repository declaration into a live deployment claim. Light and dark, keyboard navigation, URL history and card-first interaction are acceptance requirements.

## Ships now and later

Now: landscape and shared membership, primary project kinds, independently supported views across the taxonomy, graph cards/flows for request, game-loop, ECS and declared infrastructure, evidence inventory, draft/update persistence, Jev selection/caching, schema/build validation, tests, documentation and browser checks on a real game monorepo plus an API fixture.

Later: automatic source-level tracing and complete import parsing for every language; trace replay/timing overlays; full sequence-diagram lifelines, ECS archetype tables, nested infrastructure region/cluster layout; live-cloud discovery and deployed-state verification. Those need evidence or rendering capabilities beyond this change. A generic graph is shipped for the other kinds above; it must be described honestly as such.

## Acceptance

Hermetic pipeline tests exercise acceptance, rejection, abstention, caching/invalidation, unsupported-language evidence, legacy drafts, sharing and malformed references. Viewer checks cover landscape → project → view → source component navigation, loop/branch graphs, displayed-only legends and both themes. Run `npm test`, rebase onto `codemap-lenses` before integration, commit only on `codemap-project-types`, and report concrete artifacts and any evidence gaps. All generated maps and API credentials used for verification stay in temporary stores; nothing writes to the user's codemap store.
