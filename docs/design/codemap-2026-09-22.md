# Codemap: a multi-level architecture map that agents build and Jev keeps consistent

Designed 2026-09-22. Status: v1 specification for the `codemap` skill. Later phases (map diff, animation) are recorded at the end and tracked in Beads.

## Purpose

Give human engineers one artifact that answers "how is this codebase structured, and what depends on what" at the altitude they need, from a single screen down to files. The skill must produce the same map shape every run for the same code: deterministic scripts do everything mechanical, the agent writes prose grounded in repository evidence, and Jev (TypeSafe's typed-decision model through Vercel AI Gateway) makes every discrete judgment call so that grouping does not drift between runs or between agents.

## Levels of abstraction

Three levels, each one screen, each answering one question. A fourth, analytical lens sits beside them.

| Level | Name | What is drawn | Answers | Bounds |
| --- | --- | --- | --- | --- |
| L0 | System picture | people on the left, areas with their runnable parts in the middle, the external systems the product touches on the right, runtime flows between them | What is this, who uses it, what runs, what talks to what? | ≤ 6 people, 3–7 areas, ≤ 10 runnables drawn, ≤ 8 externals |
| L1 | Area | one area's components in the runtime × role matrix, ghosts for touched components of other areas, supporting tray beneath | Inside this area, what are the parts, where do they run, which feed which? | ≤ 12 product components per area |
| L2 | Component | modules of one component, files listed on the card | Inside this component, where does each responsibility live? | ≤ 16 modules |
| lenses | Purpose · Layers · Ships in · Size & activity | see Lenses below | one question each | whole system |

The map stops at files. Every L2 leaf links to a path; reading code is the editor's job.

### Areas

An **area** is a group of parts one kind of person uses for one purpose: *Playing*, *Authoring worlds*, *Serving a World*, *Operating*. The principle is fixed by the skill because it is the decomposition people already draw and it survives across repositories (a SaaS has customers, admins, and operators; a library has consumers and maintainers). Every area must hold at least one **runnable** product component; groups of supporting code alone are not areas. One implicit area, **Build & verify**, holds every supporting component (tooling, tests, docs, experiments) and the development-time externals, and is drawn as a distinct region at the bottom of the system picture. The agent proposes the areas with definitions; Jev assigns each component to one.

A **runnable** is a product component with the `surface` role that starts as its own process or page: it has an executable entry, or a `client`, `server`, or `cli` runtime. A library that ships a helper binary (a migration tool inside a storage crate) is not a runnable. Runnables are what the system picture draws inside each area; the area's libraries are summarized as a chip and shown on L1.

### Flows

Imports say which code uses which code; they cannot say that the client talks to the gateway over HTTP or that the world server loads content files. The agent writes **flows** from the repository's own documentation: `{from, to, label, kind}` where endpoints are runnables, people, or externals, `label` names the mechanism ("WebSocket, binary protocol", "reads content/worlds"), and `kind` is `network`, `file`, or `process`. Flows are the arrows of the system picture. Import edges between areas are available on hover, never the primary picture.

### People and externals

People (`actors`) carry `uses`: the runnables or areas they touch, at most two, so arrows stay legible. Externals carry a `kind`: `datastore` (drawn as a cylinder), `service` (a cloud), `runtime` (a device: browser, desktop wrapper, embedded engine), or `devtool` (Blender, Playwright, package managers), and `used_by`. Only datastore, service, and runtime externals appear on the system picture; devtool externals are chips inside Build & verify.

## Three facts about every component

The first review of a real map showed that one grouping cannot carry everything an engineer asks: "what is this for", "where does it run", and "is this even product code" are three different questions. Every component therefore carries three independent attributes, each a Jev Choice with evidence from the scan and the draft:

| Attribute | Question it answers | Values |
| --- | --- | --- |
| `area` | Who uses it, for what? | one of the proposed areas, or Build & verify |
| `runtime` | Where does it run? | `server` (a long-lived service process), `client` (a page or desktop app a person uses), `shared` (a library compiled into more than one runtime), `cli` (a command run by a person or a script), `build` (runs only while building or developing), `none` (not executable: content, docs) |
| `nature` | What kind of code is it? | `product` (runs as part of what users use, including the authoring tools designers operate), `tooling` (build, dev stack, quality gates, asset pipelines), `test` (harnesses, acceptance lanes, test support), `content` (data and scripts the product loads), `docs` (documentation and review evidence), `experiment` (prototypes and spikes) |

Product components also carry a `role`, the hexagonal position that makes the dependency rule checkable: `surface` (what a person or another system touches: UI, API handlers, CLI entry points, editor hosts), `adapter` (I/O and engines: persistence, transport, rendering, filesystem, OS and browser APIs), `core` (the system's own rules, models, sessions, workflows), `kernel` (types, schemas, utilities every role shares). Drawn top to bottom in that order, healthy dependencies point down: surface uses adapters and core, adapters implement for core, core rests on the kernel. Core reaching into an adapter is the one upward arrow that matters. Non-product components have role `none`.

The scanner supplies `hints` per unit from its manifests so these choices rest on evidence rather than names: executable targets (`src/main.rs`, `[[bin]]`, package `bin`), wasm targets (`cdylib`), server libraries (axum, tokio, express, fastify, django), browser libraries (three, react, vite, dom), desktop wrappers (electron, tauri), test frameworks (vitest, playwright, pytest), and whether the unit lives under a `tools`, `tests`, `docs`, `content`, or `prototypes` directory.

## Lenses

Revised after the first real map was read by people (see "UX review" below). A codebase can honestly be seen from above in more than one way, and each way answers a different question, so the whole system has four lenses over the same components, hue, and selection:

| Lens | Question | Layout |
| --- | --- | --- |
| Purpose | Who uses what, and how do the running parts talk? | the system picture (L0) |
| Layers | Where does each part run, and which way do its dependencies point? | runtime × role matrix over product code only |
| Ships in | Which libraries end up inside each app, service, and command? | library × runnable matrix from transitive production imports; filled dot direct, ring through another library |
| Size & activity | Where is the code, and where is work happening? | treemap grouped by area, tiles sized by lines, shaded by file changes in the 90 days before the scanned commit |

Hue is the area everywhere. The map opens on Purpose with a start-here panel: the one-sentence `summary`, the flows in reading order, and the lenses with their questions. Switching lens keeps the selection. L1 uses the Layers matrix for one area; L2 lists modules.

### UX review (2026-09-22)

Reading the ue-mmo map showed: no start-here (the landing panel was a 150-word paragraph); flow pills cut mid-phrase so the main story was unreadable; pipeline words on screen (L0/L1/L2, Jev percentages, instability, fan in/out, "finding 55%"); a static legend listing every glyph; the whole-system matrix unreadable at fit and dominated by supporting code; flat crates showing one "root" module plus tests drawn as product; generated module sentences that restate the directory name; and a final report that was a stats dump. The fixes: the four lenses above; `summary` plus a short flow `label` with a `detail`; plain words on screen (layer, unsure, undecided, used by, uses, "worth a look", "fine by design", headline names for the checks); a legend of only what the screen draws; product-only Layers; flat roots split into per-file modules, test modules in their own band, dense module graphs drawn as structure with imports on hover; generated module sentences hidden; and a report that leads with the story and the lens for the user's question.

## Health checks

"Smells" become named checks with a one-sentence meaning, an evidence pointer, and, where judgment is needed, Jev's verdict. A finding is shown only when it exists; the panel reads "4 checks, 2 findings".

| Check | Meaning shown to the reader | Decided by |
| --- | --- | --- |
| `cycle` | These components import each other, directly or through others, so neither can change alone. Module cycles that pass through a component's root module (`lib.rs`, `index.ts` re-exporting and being imported back) are the ordinary hub pattern and are not reported. | scanner |
| `core-uses-adapter` | A core component imports an adapter, so its rules are tied to one storage, transport, or engine. | Jev Boolean: acceptable by design? |
| `crosses-the-wire` | Client code imports server code (or the reverse) directly instead of a shared contract. | Jev Boolean: acceptable by design? |
| `product-uses-support` | Product code imports tooling, test, or experiment code, which can ship or break the build. | scanner |

Test-only imports never produce findings.

## Pipeline

```
scan ──▶ skeleton ──▶ enrich (agent) ──▶ decide (Jev) ──▶ build ──▶ review
 │           │             │                  │              │
 scan.json   skeleton.json  draft.json         decisions.json map.json + index.html
```

All scripts are Python 3 standard library, under `skills/codemap/scripts/`, invoked as `python3 <skill-dir>/scripts/codemap.py <command>`. Every command reads and writes only inside the map store, prints a JSON summary, and exits non-zero with a JSON `{"status":"error","error":"…"}` on stderr when it cannot complete.

### 1. `scan` (deterministic)

Input: repository root and the ref to scan (default `HEAD`). Enumerates tracked source files via `git ls-files`, detects language by extension, counts lines, and extracts imports:

| Language | Import forms | Resolution |
| --- | --- | --- |
| TypeScript, JavaScript | `import … from`, `export … from`, `import()`, `require()` | relative paths (with extension and index probing), `tsconfig` `paths`, workspace package names to package roots; else external |
| Rust | `use crate::…`, `use <crate>::…`, `mod x;`, `extern crate` | crate-internal paths to files; workspace crate names via `Cargo.toml` `[dependencies]` to crate roots; else external |
| Python | `import a.b`, `from a.b import c`, relative `from .x import` | package roots discovered from `pyproject.toml`, `setup.cfg`, or `__init__.py` chains; else external |

Units are detected from workspace manifests first (`pnpm-workspace.yaml`, `package.json` workspaces, `Cargo.toml` `[workspace]`), then `pyproject.toml`/`setup.py` directories, then, when no manifest claims a source file, its top-level directory. A manifest-less directory with at least 40 source files and two or more first-level subdirectories of at least 8 files each splits into one unit per such subdirectory (`tools/perf`, `tools/character`), so unrelated pipelines under one folder do not become one blob; smaller subdirectories and loose files stay in the parent unit. Assets and generated trees are excluded by a default ignore list (`node_modules`, `target`, `dist`, `build`, `.git`, binary extensions) plus `.gitignore` handling by `git ls-files` itself.

Output `scan.json`:

```json
{"schema": "codemap.scan/1", "repo": {"root": "…", "remote": "…", "ref": "HEAD", "sha": "…", "branch": "…"},
 "scanned_at": "2026-09-22T10:00:00Z",
 "units": [{"id": "world-renderer", "path": "packages/world-renderer", "kind": "package|crate|app|python|directory",
            "name": "@ue-mmo/world-renderer", "manifest": "packages/world-renderer/package.json",
            "description": "manifest description if any", "readme": "packages/world-renderer/README.md"}],
 "files": [{"path": "packages/world-renderer/src/scene/graph.ts", "lang": "ts", "loc": 212, "unit": "world-renderer"}],
 "edges": [{"from": "packages/world-renderer/src/scene/graph.ts", "to": "packages/content-schema-ts/src/index.ts",
            "specifier": "@ue-mmo/content-schema-ts", "line": 3}],
 "externals": [{"name": "three", "count": 41, "files": ["…"]}],
 "unresolved": [{"from": "…", "specifier": "…", "line": 9}]}
```

Each file carries a `role` (`source` or `test`, by directory and basename convention). Files and edges are sorted by path; identical inputs produce byte-identical output.

### 2. `skeleton` (deterministic)

Turns the scan into the mechanical part of the map: L2 candidates are units; L3 modules are the first-level directories under a unit's source root (files directly in the root form a module named after the unit), any directory with one file folds into its parent. Computes per-node metrics, aggregates file edges to module and unit edges with production `count`, `test_count`, a `test_only` flag, and three example imports, detects cycles (Tarjan) over production edges only, and emits `skeleton.json` with the same node and edge shapes as `map.json` minus prose and decisions. Ordering and IDs are stable slugs derived from paths.

### 3. `enrich` (agent, guided by SKILL.md)

The agent reads what the repository says about itself, in this order of authority: architecture inventories and ADRs, glossary or `CONTEXT.md`, READMEs, manifest descriptions, directory names. It writes `draft.json`:

- `system`: name, one-paragraph purpose, `actors` (people who use it, each with `uses`: up to two runnables or areas), `externals` (systems it depends on, each with a `kind`: datastore, service, runtime, devtool, and `used_by`), and `flows` (runtime connections between runnables, people, and externals with a mechanism label).
- `areas`: 3–7 areas, each a group of parts one kind of person uses for one purpose, with an `id`, a `name` in the repository's vocabulary, a `definition` that distinguishes it from its neighbors, and the product `components` the agent expects in it. Supporting components need no listing; they land in Build & verify or with the area they serve.
- `components`: for every unit, `responsibility`, `why`, `entry_points`, `evidence`.
- `edge_reasons`: one line per unit-to-unit edge saying what the dependency is for, written from the example imports.
- `module_names`: optional human names for L3 modules whose directory name is opaque.

Every sentence must trace to evidence the agent read; the skill's quality bar for these sentences lives in `references/enrichment.md`.

### 4. `decide` (Jev)

Jev answers typed questions; it writes no prose. The script builds each request from `skeleton.json` and `draft.json`, sends it through Gateway, validates the answer, and caches it under a fingerprint of the exact state it was asked about. Re-running with unchanged state reuses the cached answer, which is what keeps maps stable across runs and agents.

| Decision | Primitive | State | Options |
| --- | --- | --- | --- |
| Area of each component | Choice | component card, manifest hints, its dependencies' and dependents' names and responsibilities, external libraries, sample paths | the proposed areas with definitions, `build_verify` (supporting code that serves no single area), `new_area` ("none fits"), `abstain` |
| Runtime of each component | Choice | same card | `server`, `client`, `shared`, `cli`, `build`, `none`, `abstain` |
| Nature of each component | Choice | same card | `product`, `tooling`, `test`, `content`, `docs`, `experiment`, `abstain` |
| Role of each product component | Choice | same card | `surface`, `adapter`, `core`, `kernel`, `abstain` |
| Core-uses-adapter acceptable | Boolean | both cards, roles, example imports | `true` = acceptable by design, `false` = finding |
| Crosses-the-wire acceptable | Boolean | both cards, runtimes, example imports | `true` = acceptable by design, `false` = finding |
| Assignment still holds (updates only) | Boolean | previous decisions, the change summary since the map's commit | `true` keeps the cached decisions |

The four per-component Choices travel in one request sharing the card. Instructions per question are fixed, versioned strings in `decide.py`; `references/jev-decisions.md` explains them. The rubric for area assignment: place the component with the people who use it, judging by responsibility rather than by who imports it; a library every area uses belongs to the area that owns its vocabulary; supporting code belongs to the area it serves, or to Build & verify when it serves the repository itself.

Thresholds: confidence ≥ 0.6 accepted; 0.4–0.6 accepted and flagged `uncertain` on the card; below 0.4, `abstain`, or `new_area` leaves the node **unresolved**. The agent must add evidence to the draft and re-run `decide` once; a node still unresolved lands in a visibly distinct `Unsorted` group rather than in an invented home. A Gateway failure or missing key stops the pipeline with the model-routing setup instructions; there is no agent fallback for decisions.

`decisions.json` records for every decision: node id, question id, state fingerprint, answer, probabilities, confidence, model, elapsed seconds, cost when returned, and the instructions version.

### 5. `build` (deterministic)

Merges skeleton, draft, and decisions into `map.json`, validates it, computes level-appropriate aggregate edges, and renders `index.html` by embedding the JSON into `assets/viewer.html`. Validation fails on: any file outside a module, any module outside a component, any component without a resolved or explicitly unresolved area, runtime, or nature, a product component without a role, an area count outside 3–7, an area without a runnable, a flow with an unknown endpoint, an L1 or L2 edge without a reason, a node without a responsibility, a dangling edge. Serialization uses sorted keys and stable ordering so two builds of the same inputs are byte-identical.

`map.json` (schema `codemap.map/1`):

```json
{"schema": "codemap.map/1", "meta": {"repo": {…}, "built_at": "…", "skill_version": "…", "jev_model": "typesafe-ai/jev", "instructions_version": 1},
 "system": {"id": "system", "name": "…", "purpose": "…", "actors": [{"id": "…", "name": "…", "role": "…"}], "externals": [{"id": "…", "name": "…", "role": "…", "used_by": ["component-id"]}]},
 "areas": [{"id": "playing", "name": "Playing", "definition": "…", "hue": 210, "components": ["web-client", "…"], "runnables": ["web-client"], "counts": {"product": 7, "supporting": 2, "runtimes": {"client": 6, "…": 0}}}],
 "flows": [{"from": "web-client", "to": "gateway", "label": "HTTPS: account login, world tickets", "kind": "network"}],
 "components": [{"id": "sim-core", "name": "sim-core", "path": "crates/sim-core", "kind": "crate", "area": "serving", "runnable": false, "runtime": "shared", "nature": "product", "role": "core",

              "files": [{"path": "…", "loc": 120, "exports": ["…"]}], "metrics": {…}}],

```

### 6. `review` (agent)

The agent opens the built map's summary, checks the validation report and the unresolved list, spot-reads five cards against the code, and reports the map path, counts per level, unresolved nodes, and smells to the user.

## Update flow

`codemap.py update` re-scans, rebuilds the skeleton, and diffs the new scan against the previous one into `changes.json`: per component, files added, removed, or changed and unit-level dependencies gained or lost, plus lists of new and removed components. It merges the draft (template entries for new components and edges, stale entries dropped, written prose kept) and, when the draft has no gaps, runs `decide`; otherwise it reports the gaps for the agent to fill before `decide` and `build`. `decide` picks up a pending `changes.json` whose commit matches the skeleton, asks the "assignment still holds" Boolean for changed components whose cards no longer match their cached fingerprints (a `true` carries the previous area, runtime, nature, and role forward; a `false` re-asks them), asks the full set for new components, and consumes the changes file on success. Areas are never renamed during an update unless a component returns `new_area`; then the agent revises the areas in the draft.

## Storage

Everything lives outside the repository under `~/.furanku-skills/codemap/<repo-key>/` where `repo-key` is `<repo-basename>-<first 8 hex of sha1(absolute repo root)>`. `FURANKU_SKILLS_HOME` overrides `~/.furanku-skills` so tests stay hermetic.

```
<repo-key>/
  scan.json  skeleton.json  draft.json  decisions.json  map.json  index.html
  snapshots/<sha>/map.json        one immutable copy per built commit (the raw material for diffs)
  codemap.log                     one line per command: time, command, ref, sha, outcome
```

The Gateway key is the one model-routing saves at `~/.furanku-skills/model-routing/secrets/gateway.json`, or `AI_GATEWAY_API_KEY` for the current process. Codemap ships its own small client (Choice, Score, Boolean) with the same transport rules as model-routing: TypeSafe-only routing, no redirects or retries, bounded payload and response, one deadline per call, errors that never echo provider bodies.

## Viewer

One self-contained `index.html`, no network, no build step, opens from disk. It is the product.

**Visual grammar.** Each visual channel carries exactly one meaning, the same at every level:

| Channel | Meaning |
| --- | --- |
| Hue | area (legend at the bottom) |
| Column | runtime, each with an icon: client (window), shared (two arrows), server (rack), cli (prompt), build (wrench) |
| Row | role: surface, adapter, core, kernel, top to bottom |
| Node shape | kind of thing: person pill, runnable rectangle, flat library, external cylinder/cloud/device, area region; within components, nature: product solid, tooling outlined, tests dashed, content and docs a document with folded corner, experiments dotted |
| Node corner icon | runtime, so a node keeps its "where" even in the purpose lens |
| Edge | solid arrow for a production import, thickness by count; dotted faint for test-only; red dashed for a health finding |
| Badge | amber dot for an uncertain decision, `?` for unresolved |

**Kinds of things look different.** A person is a pill with a person icon. A runnable is a strong-bordered rectangle with its runtime icon and a subtitle naming what it is ("Rust service", "Vite web app", "Node CLI"). A library is a flat, thin-bordered rectangle, shown only inside areas. An external is gray and dashed: a cylinder for a datastore, a cloud for a service, a device outline for a runtime. An area is a large tinted region with a title, not a card. Build & verify is an outlined region at the bottom holding supporting components as small chips grouped by nature, plus devtool externals.

**Screens.** The four lenses above, then Area (L1) and Component (L2); `references/viewer.md` is the current description of each.

**Navigation.** Breadcrumb, explicit back and forward buttons wired to browser history (hash routes), `Esc` up, `/` search across every level, `1`–`4` switch lens, `t` theme, `h` health, `0` fit. Clicking a node selects it and shows its card; clicking the selected node, double-click, or `Enter` zooms in with a 250 ms transition.

**Interaction.** Hovering a node highlights what it depends on in one hue and what depends on it in another and dims the rest. Clicking an edge shows its reason and example imports. Layout is deterministic: barycenter ordering within cells, ties by id, no physics.

Restrained palette, system font stack, motion 200–300 ms. Nothing decorative that does not carry information.

1. **Map diff from git.** Build the map at two refs (commits, branches) reusing cached decisions so only code changes move the picture, then compare `snapshots/<sha>/map.json` structurally: added, removed, moved, and re-layered nodes; new, dropped, and strengthened edges. Present before/after, overlay, and change-list views in the viewer.
2. **Animated transitions between snapshots**, playing a commit range as motion in the map.
3. More languages (Go, Java, C#) as scanner modules with the same output contract.
