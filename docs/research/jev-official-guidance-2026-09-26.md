# Official TypeSafe Jev guidance for retrospective judgments

Checked 2026-09-26 against TypeSafe's [documentation index](https://docs.typesafe.ai/llms.txt). This note records provider guidance, then audit implications; it does not measure this repository's implementation or Jev's accuracy on its data.

## Documented behavior and guidance

- **Question isolation.** One request shares a `state`, but each question is evaluated independently and in parallel. An answer to one question is not context for another. Question IDs are response keys for code and are **not sent to the underlying model**: the judgment must be complete in `instructions`. A genuinely dependent second judgment requires a subsequent request. [Primitives](https://docs.typesafe.ai/primitives.md), [State](https://docs.typesafe.ai/concepts/state.md), [API reference](https://docs.typesafe.ai/api.md).
- **Visible criteria.** For a Choice, option names **and** descriptions are sent to the model. Include an `other`/`none` option when the option set may be incomplete. For a Score, each level is evaluated separately: Jev does **not** see its numeric position or neighboring levels. Descriptions must stand alone, identify observable situations, and cover boundary cases. Score is a probability-weighted mean of level numbers; it is not a measured physical magnitude. Noul is an absolute yes probability, whereas Choice chooses relatively among listed options, so a Choice winner is not proof that any option fits. [Choice](https://docs.typesafe.ai/primitives/choice.md), [Score](https://docs.typesafe.ai/primitives/score.md), [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), [Line-by-line search](https://docs.typesafe.ai/cookbooks/semantic_find.md).
- **Atomic decisions and code composition.** TypeSafe recommends one focused judgment per question, one Score dimension per scale, and combining independent dimensions with deterministic weights in code. Normalize Scores before weighting when scales have different level counts. Jev 1.13 is weak at counts, date comparisons, arithmetic, precise numeric interpolation, and multi-hop instructions; those operations belong in code. Keep instructions and criteria aligned, and spell out the intended condition. [Primitives](https://docs.typesafe.ai/primitives.md), [Score](https://docs.typesafe.ai/primitives/score.md), [Composite scoring](https://docs.typesafe.ai/patterns/composite-scoring.md), [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md).
- **State selection.** A JSON object with descriptive field names is recommended for related context; all questions in a request see the same state. Jev 1.13's accuracy declines with irrelevant material in a large state, so retrieve/filter first and send fields germane to the question. Its current published budgets are 64k tokens across a request and 32k for state plus the longest question; these are limits, not evidence that a large state is equally accurate. The docs advise a relevance filter when upstream filtering is unavailable. [State](https://docs.typesafe.ai/concepts/state.md), [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), [Models](https://docs.typesafe.ai/models.md), [Classifying RAG passages](https://docs.typesafe.ai/cookbooks/classifying_rag_passages.md).
- **Confidence and abstention.** Choice/Score `confidence` summarizes how concentrated their probability distribution is; it does not guarantee correctness. Noul has no separate confidence field; its `noul` value is the yes probability. TypeSafe recommends action/review/abstain bands chosen for the cost of error, with thresholds tested on one's own data. It also cautions against transferring thresholds between Noul and Choice. Pin and log the returned versioned model ID if thresholds are tuned for a version, since `jev-latest` can move. [Confidence](https://docs.typesafe.ai/confidence.md), [Noul](https://docs.typesafe.ai/primitives/noul.md), [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), [Models](https://docs.typesafe.ai/models.md).
- **Evidence and citations.** A Choice over candidate passages always selects a winner because its probabilities sum to one, even if no passage answers the question. The semantic-find recipe pairs that Choice with a Noul asking whether an answer exists and says to tune thresholds on one's own documents. The citation-check recipe first tests whether a quoted span occurs in the source with ordinary string matching, then gives the claim and surrounding section to a three-way Choice (`supports`, `contradicts`, `says_nothing`); exact quote presence alone is insufficient. Low-confidence relationship judgments receive human review. [Line-by-line search](https://docs.typesafe.ai/cookbooks/semantic_find.md), [Double-checking citations](https://docs.typesafe.ai/cookbooks/citation_check.md).

## Implications to test for retrospective work-domain and outcome scoring

These are **inferences from the guidance**, not findings about this repository. Domain labels hidden only in question IDs will not inform Jev; put the domain decision and domain boundaries in instructions and Choice criteria. A one-call domain Choice can force an unrelated work item into a listed domain, so include a none/other path or separately test fit. Outcome rubrics framed only as numbers or relative terms (for example, “better than prior level”) leave Jev without standalone semantics. An outcome that combines completion, user value, evidence quality, and confidence should be decomposed if these are genuinely separate judgments; code should own aggregation. Evidence retrieval should preserve source identifiers and nearby context and verify that the **claim** is supported, not merely that a passage looks relevant. These deductions follow the [Choice](https://docs.typesafe.ai/primitives/choice.md), [Score](https://docs.typesafe.ai/primitives/score.md), [Composite scoring](https://docs.typesafe.ai/patterns/composite-scoring.md), and [citation-check](https://docs.typesafe.ai/cookbooks/citation_check.md) guidance.

Before calling Jev unsuitable for this use, build a small, adjudicated set of real retrospective examples spanning ordinary, ambiguous, absent-evidence, and hard boundary cases. Compare the present payload against focused variants that change one factor at a time: explicit instructions/criteria, relevant state fields, separate atomic scores, and a none/abstain path. On held-out examples, measure domain and outcome accuracy, evidence-support accuracy, coverage at proposed confidence thresholds, and errors among high-confidence answers. Pin the model version and compare with a simple deterministic or human baseline. This is a proposed evaluation design grounded in TypeSafe's advice to test level wording and thresholds on one's own data, inspect errors, and test edge cases; the docs do **not** promise that any primitive or rewrite will fix accuracy. [Score](https://docs.typesafe.ai/primitives/score.md), [Confidence](https://docs.typesafe.ai/confidence.md), [How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md), [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md).

## Gateway contract and remaining unknowns

TypeSafe's own endpoint is `POST https://api.typesafe.ai/v1/systemone`, with `state`, `model`, and keyed `questions`. Vercel documents two distinct ways to call Jev through AI Gateway:

| Endpoint | Yes/no type and answer | Score criteria | Model name |
| --- | --- | --- | --- |
| [`POST /v1/evaluate`](https://vercel.com/docs/ai-gateway/modalities/evaluation) | `boolean` → `probability` | Ordered array of at least two labels (documented as strings) | `typesafe-ai/jev` |
| [`POST /typesafe/v1/systemone`](https://vercel.com/docs/ai-gateway/sdks-and-apis/typesafe) | `noul` → `noul` | TypeSafe request and response shape | `typesafe-ai/jev` |

Vercel says the compatible endpoint preserves the TypeSafe shape, while its general evaluation endpoint uses different naming. TypeSafe's structured Score levels can be objects or arrays in its own API, but Vercel's `/v1/evaluate` page only documents an array of string labels; object-level support there is **unknown**. The `/v1/evaluate` Choice and Score HTTP examples show probabilities and scores but omit `confidence`. The [AI SDK evaluation reference](https://ai-sdk.dev/docs/ai-sdk-core/evaluation#probabilities-and-confidence) says TypeSafe-specific Choice/Score confidence is in `result.providerMetadata?.typesafe?.confidence`, keyed by question ID, in the SDK result; it is not the selected option's probability or a portable statistic. The exact confidence presence and location in this repository's raw `/v1/evaluate` HTTP response should therefore be verified on wire data before a parser or gate depends on it. Vercel documents Gateway usage as `inputTokens`/`outputTokens` and `providerMetadata`, whereas the TypeSafe-compatible endpoint uses `input_tokens`/`output_tokens` and `provider_metadata`. These are contract distinctions, not evidence of comparative accuracy. [Vercel evaluation](https://vercel.com/docs/ai-gateway/modalities/evaluation), [Vercel TypeSafe-compatible API](https://vercel.com/docs/ai-gateway/sdks-and-apis/typesafe), [TypeSafe API](https://docs.typesafe.ai/api.md), [TypeSafe Score](https://docs.typesafe.ai/primitives/score.md).

Neither official reference establishes this repository's measured accuracy on retrospective data. That requires its actual wire payloads, reference cases, and outcome comparison.
